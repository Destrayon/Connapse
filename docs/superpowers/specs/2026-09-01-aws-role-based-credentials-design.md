# AWS role-based credentials for the Connapse sync identity

**Status:** Design — approved in brainstorming, pending spec review
**Date:** 2026-09-01
**Branch context:** builds on `epic/aws-per-user-permissions`

## Problem

The AWS provider "Access" step provisions Connapse's own sync identity as an
IAM **user** with a long-lived, DataProtection-encrypted static access key
(`connapse-reader`, generated by
[`AwsIamUserSetup`](../../../src/Connapse.Core/Utilities/AwsIamUserSetup.cs)).
AWS best practice is to avoid long-lived access keys in favor of roles and
temporary credentials. Connapse is self-hosted, and hosting splits roughly
into two populations:

- **On AWS** (EC2 / ECS / EKS) — a minority — can use an ambient instance /
  task role and store no secret at all. The runtime already prefers ambient
  credentials via `DefaultAWSCredentialsIdentityResolver` in
  [`ConnapseAwsCredentials`](../../../src/Connapse.Storage/CloudScope/ConnapseAwsCredentials.cs).
- **Off AWS** (on-prem, other clouds, laptops) — the majority — cannot get an
  instance role. Today their only easy path is the IAM user + static key.

Goal: make a **role** the easy, default path for both populations and support
multiple Connapse instances on one AWS account without collisions. The IAM user
+ static key path is **removed entirely** — it is pre-release with no users, so
there is no migration burden and no reason to carry a discouraged credential
shape forward.

## Non-goals

- Reworking the **per-user permissions** feature (S3 Access Grants + SAML /
  Identity Center). It is already role- and grant-based and stores no per-user
  credential; it is out of scope here.
- Shipping the external `aws_signing_helper` Go binary. The Roles Anywhere
  signing is implemented natively in C# (see §3).
- Standing up a Connapse certificate authority. Rejected in favor of
  per-instance trust anchors (see §4).

## Decisions (from brainstorming)

1. **Auto-detect** the credential mode on page load; surface it as a
   traffic-light status on the Access step (green / yellow / red).
2. Deliver the **full Roles Anywhere path now** (native provider + local
   keypair + easy setup script), not as a fast-follow.
3. Support a **bring-your-own-role** escape hatch (admin supplies their own
   ARNs / cert).
4. Multiple instances **share role + profile + policy**; each instance gets its
   **own trust anchor**. Setup is idempotent (reuse-if-present).
5. Do **not** treat Connapse's runtime identity as permanently read-only. Reset
   attempts a direct AWS revoke and degrades gracefully; the permission
   preflight checks a declared required-actions set, not a frozen read-only
   list.
6. **Remove the IAM user + static access key path entirely** — no fallback, no
   back-compat shim. It is pre-release with no users.

## Credential modes

Resolved at runtime in priority order:

| Mode | Where | Stored secret | Setup |
|------|-------|---------------|-------|
| **Ambient role** | On AWS (instance / task role, IRSA) | none | attach a role; auto-detected |
| **Roles Anywhere** | Off AWS | private key (encrypted), local | easy script or manual values |

**Removed:** the IAM user access key mode. The existing
[`AwsIamUserSetup`](../../../src/Connapse.Core/Utilities/AwsIamUserSetup.cs) and
its access-key branch in `ConnapseAwsCredentials` are deleted as part of this
work (see §2, §5, "Delivery shape").

## §1 Adaptive Access card + detection

Detection runs on page load and drives the status shown by the existing
`ProviderStepCard` model, computed in
[`ProviderSetupReader`](../../../src/Connapse.Web/Services/ProviderSetupReader.cs):

- **Green** — a credential resolves (ambient role, or configured Roles Anywhere)
  **and** the permission preflight passes.
- **Yellow** — an identity resolves but the preflight finds missing
  permissions. The card lists exactly which actions were denied (e.g.
  `s3:ListBucket denied`) and how to fix them.
- **Red** — nothing resolves; the card shows the setup choices.

**Permission preflight.** A "try the reads the app actually needs" probe that
attempts each action in a **declared required-actions set** and maps every
`AccessDenied` to the missing action. The set is data, not a hardcoded
read-only list, so adding write actions later extends the set without a
redesign. Initial set: `sts:GetCallerIdentity`, `s3:ListAllMyBuckets`, a scoped
`s3:ListBucket` + `s3:GetBucketLocation`, and — when per-user permissions are
enabled — `s3:ListAccessGrants` plus the `identitystore` reads already required
by [`AwsSearchScopeResolver`](../../../src/Connapse.Storage/CloudScope/AwsSearchScopeResolver.cs).

## §2 Runtime credential resolution

[`ConnapseAwsCredentials`](../../../src/Connapse.Storage/CloudScope/ConnapseAwsCredentials.cs)
(a `RefreshingAWSCredentials`, 5-minute refresh window) gains a mode switch in
`GenerateNewCredentials()`:

- **Roles Anywhere** → a new native provider performs a SigV4-X509 `CreateSession`
  request to `rolesanywhere.<region>.amazonaws.com/sessions`, signed with the
  instance's cert + private key, returning temporary credentials refreshed on
  the existing window. No external helper binary.
- **Ambient** → the current `DefaultAWSCredentialsIdentityResolver` fallback,
  unchanged.

The existing static-access-key branch is **removed** from
`GenerateNewCredentials()`.

The native signer is the one genuinely novel component: it builds the canonical
`CreateSession` request, signs the request hash with the X.509 private key, and
attaches the cert in the `X-Amz-X509` header per the Roles Anywhere signing
scheme.

## §3 Roles Anywhere easy-setup handshake

The private key never leaves the host, so setup is a two-way handshake rather
than a one-shot paste-back:

1. **Connapse generates locally** a keypair + self-signed cert on the setup
   host. The private key is stored via DataProtection (same protector used for
   the access key today). The **public cert PEM** is displayed in the UI.
2. **Admin runs a CloudShell script** — generated by a new
   `AwsRolesAnywhereSetup` in `Connapse.Core/Utilities`, mirroring
   `AwsIamUserSetup` — pasting in that cert. The script:
   - **Reuses if present** (idempotent, guarded by the `CreatedBy=Connapse`
     tag): the **role**, the **`ConnapseRead` policy** (from
     [`S3SetupPolicy`](../../../src/Connapse.Core/Utilities/S3SetupPolicy.cs)),
     and the **profile**. Describe-then-create, never blind-create — this is
     what lets a second instance on the same account succeed instead of getting
     stuck.
   - **Always creates its own** trust anchor from the pasted cert (per-instance;
     no collision possible).
   - Prints a `----- BEGIN CONNAPSE AWS ROLE -----` block with three ARNs
     (trust-anchor, profile, role) + region — all non-secret.
3. **Admin pastes the ARN block** back into Connapse. It is parsed (as
   `AwsIamUserSetup.ParseResult()` does today) and stored. Connapse can now vend
   its own temporary credentials.

**Required setup permissions** (CloudShell admin creds, not runtime):
`iam:GetRole`, `iam:CreateRole`, `iam:PutRolePolicy`, `iam:ListRoleTags`,
`rolesanywhere:CreateTrustAnchor`, `rolesanywhere:CreateProfile`,
`rolesanywhere:ListProfiles`, `sts:GetCallerIdentity`.

## §4 Manual values

Same runtime provider, script skipped. Consistent with how every provider card
already supports entering values by hand, the card lets an admin type in their
own trust-anchor / profile / role ARNs and optionally supply their own cert +
key instead of Connapse's generated pair — for admins who provisioned the AWS
side themselves rather than running the generated script. This is the standard
manual-entry affordance, not a special mode. On-AWS admins who prefer a
hand-crafted instance role use the ambient path with nothing to configure.

**Why per-instance trust anchor over a shared CA:** each instance holds its own
private key (keeping the "key never leaves the host" property), so certs differ
per instance. A single shared trust anchor would require a Connapse CA whose key
signs each instance cert — real key-management overhead. Per-instance trust
anchors need no CA, and are independently revocable (a feature, see §8). All
instances still share one role + one policy managed in one place.

## §5 Storage

There is now a **single stored credential shape** (Roles Anywhere), so no `Kind`
discriminator is needed. Ambient mode stores no row; a stored row therefore
always means Roles Anywhere.

Reshape
[`ProviderCredentialEntity`](../../../src/Connapse.Storage/Data/Entities/ProviderCredentialEntity.cs)
to the Roles Anywhere fields, replacing the old `PublicId` / `SecretProtected`
access-key columns:

- `CertificatePem` (cleartext — it is public)
- `PrivateKeyProtected` (DataProtection ciphertext, existing
  `ProviderCredential.v1` protector)
- `TrustAnchorArn`, `ProfileArn`, `RoleArn`, `Region`

One migration on `KnowledgeDbContext`. Because the access-key path is
pre-release with no users, the migration simply drops the old columns and adds
the new ones — no data backfill.

## §6 Error handling / fail modes

- Detection or preflight failure never crashes the page — it resolves to
  yellow / red with a diagnostic, matching the fail-closed discipline in
  `AwsSearchScopeResolver`.
- `CreateSession` failures (expired cert, revoked trust anchor, clock skew)
  surface as a clear Access-card error carrying the AWS reason, not a generic
  500.
- The idempotent setup script is safe to re-run: reuse means a rerun converges
  rather than errors.

## §7 UI changes

- Access card in
  [`Providers.razor`](../../../src/Connapse.Web/Components/Pages/Providers.razor)
  (currently the step at line ~199) becomes mode-aware: ambient shows
  status-only; off-AWS shows the Roles Anywhere handshake (easy script, with the
  standard manual-value entry from §4). The old IAM-user setup UI is removed.
- The generated cert PEM, the setup script, and the ARN paste-back field are new
  UI affordances on that card.

## §8 Reset behavior

- **Ambient mode:** hide the "Reset this step" control entirely — Connapse did
  not create the instance/task role and there is nothing it owns to reset.
  Yellow status links to the fix instead.
- **Off-AWS reset deletes only this instance's own resources:**
  - Wipe local cert, private key, and stored ARNs **first** — this instance
    stops authenticating immediately, independent of any AWS call. This is the
    part that actually protects the operator.
  - Attempt a **direct AWS revoke**: call `rolesanywhere:DeleteTrustAnchor` on
    this instance's trust anchor. If it returns `AccessDenied` (a deployment
    without the grant yet), degrade to displaying a CloudShell cleanup snippet
    that deletes just that trust anchor.
  - **Never** delete the shared role / profile / policy — that guarantee comes
    from the shared-resource design, not from a permission boundary, so it holds
    regardless of how much power Connapse's identity has.

The reset lives in
[`ProviderResetAction`](../../../src/Connapse.Web/Components/Providers/ProviderResetAction.razor);
its current IAM-user reset logic is replaced by the Roles Anywhere reset above.

## §9 Testing

- **Unit:** script generation (reuse vs. create branches), ARN-block parsing,
  SigV4-X509 signing (fixed inputs → known canonical request / signature), mode
  selection in `GenerateNewCredentials()`, preflight action→status mapping.
- **Integration:** preflight status (green / yellow / red) against a stubbed
  AWS; Roles Anywhere `CreateSession` mocked at the HTTP layer (no live AWS in
  CI, consistent with existing integration fixtures).

## Delivery shape

Sizable enough to be its **own epic with staged PRs** rather than one PR, given
the project's PR-size limit:

1. Runtime: native Roles Anywhere provider + mode switch in
   `ConnapseAwsCredentials` + storage/migration. **Removes** the static
   access-key branch and reshapes `ProviderCredentialEntity`.
2. Setup: `AwsRolesAnywhereSetup` script generator (idempotent reuse) + local
   keypair generation + ARN parsing. **Deletes** `AwsIamUserSetup`.
3. UI: adaptive Access card, detection/preflight status, reset behavior, manual
   value entry. **Removes** the old IAM-user setup UI.

Each PR references its own GitHub issue per the project's issue-first rule
(issues to be filed once this design lands on `main` and the epic is opened).
