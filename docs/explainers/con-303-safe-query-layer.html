Safe Table Queries

How agents ask questions of tables without ever touching the database directly. Ticket CON-303. About a 4-minute read.

Connapse can now hold spreadsheet-like tables, and agents can ask questions of them: show me these rows, or total this column by that one. The agent never writes a database command itself. It fills in a small structured request, and Connapse turns that into one read-only query. The query then runs as a database user that can only read table data, inside limits on time, memory and answer size. So an agent can't change data, and each request reads exactly one table in the container it is working in. Nothing else in the database is reachable.

How one question travels

Five steps, top to bottom. Purple steps happen inside the database.

  1. The agent's request

    The agent sends a small form written in JSON, a plain-text format for structured data. It names a table, some columns, and choices from fixed lists: eleven comparisons (equals, greater than, contains, and so on) and six summaries (count, count distinct, sum, average, minimum, maximum).

    The form is strict. A misspelt or unknown field is an error that says what was wrong. There is no place in it to put SQL, the language of database commands.

  2. The compiler

    The compiler is the part of Connapse that turns the form into a query. It looks up every column name in the table's catalog, which is Connapse's own record of each table and its columns. A name that isn't there is refused, with a list of the real columns so the agent can try again.

    The values the agent supplied, such as "north" or 100, travel separately as parameters: labelled slots the database fills in as data only. So a value can never become a command, whatever it contains.

    The result is always one SELECT, the database command that reads rows. One table per query; no joins across tables.

  3. The reader login

    The query does not run as Connapse's normal database user. It runs as a separate login that Connapse creates for this job. That login has been granted one thing: reading the tables in table containers.

    It is not an administrator, belongs to no group, and can't create anything. If a login with the same name already exists with extra rights, Connapse refuses to use it. Its connections are wiped clean before they are reused.

  4. The read-only transaction and its limits

    Each query runs inside a read-only transaction, a sealed unit of work in which the database refuses to save anything. When the query finishes, the transaction is always rolled back, meaning thrown away.

    • 5 seconds to finish
    • 1 second waiting on a locked table
    • 16 MB memory per sort or grouping step
    • 256 MB temporary disk
    • Always rolled back

    The time and memory limits are set twice: as the login's defaults, and again on every query. The disk cap lives on the login.

  5. The capped answer

    Answers are kept small enough for an agent to read.

    • 100 rows by default, 1,024 at most
    • 2,000 characters per text cell
    • About 50,000 characters overall

    If anything was cut, the answer carries a note saying so and how to see more. Database errors come back as plain sentences, such as "The query took longer than 5s and was stopped."

An example: total sales by region

The numbers are made up for illustration. The request format is the real one.

What the agent sends

{
  "table": "<id of the Sales table>",
  "aggregates": [
    { "aggregate": "sum",
      "column": "Amount" }
  ],
  "group_by": ["Region"]
}

In words: from the Sales table, add up Amount for each Region.

What comes back

Regionsum(Amount)
east40
north30.5
south5

Complete answer. Nothing was cut.

Had it been cut, the note would read: "More rows match; only the first 100 are shown. Use offset or a narrower filter to see more."

What's blocked, and why

There are four layers. An attack has to get past all of them to do harm. The last one, the login's grants (the list of things a database user is allowed to do), is the real wall. It holds even if the others are switched off.

Tests try each attack and prove it fails

The tests are harsher than real life. They log in as the reader and send raw database commands, which an agent can never do. Most of them first switch read-only mode off, to show the grants alone are enough.

Attack triedWhat happened
Add, change or delete rows; empty, alter or drop the tableDenied No permission, even with read-only mode off. With it on, refused as read-only too.
Read Connapse's own tablesDenied No permission.
Read server files, list folders, write a file, run a programDenied No permission.
Switch to a more powerful userDenied No permission.
Create tables, or install an add-on that reaches other serversDenied No permission.
Runaway query (a 30-second sleep)Stopped Cut off by the time limit.
Add a second command after the queryRejected The database refuses the whole thing.
Put commands in a column header or a valueHarmless Treated as plain text. Nothing was dropped.
Raise its own temporary-disk capDenied No permission.
Ask for a table in another containerNot found "There is no table with id…"

What's left, and the limits

A few small gaps remain. Every one of them needs raw database commands, which agents can't send. They would matter only if a future bug let commands through.

  • Read-only mode is a seat belt, not the wall. Someone with raw commands could switch it off. That is why the grants carry the weight, and why the tests switch it off first.
  • Temporary tables and large objects. By default, any database user may create short-lived scratch tables, and probably large objects (the database's store for big files). Both are blocked inside a read-only transaction. Connapse leaves the default alone because changing it affects the whole database; an operator can remove it.
  • The database's own listings. Every database user can read the system catalog: the database's lists of user names and who is connected. That is not Connapse data, but it is visible.
  • The reader can change its own default limits. For example, its default time limit. Connapse sets the limits again on every query and restores the defaults on every start. The temporary-disk cap is out of the reader's reach.
  • Memory is capped per step, not per query. A query with several sorting or grouping steps can use the cap several times over. The total on the smallest Azure tier has not been measured.
  • Older databases. A database upgraded from PostgreSQL 14 or earlier may still let any user create tables in the shared "public" area. The test for this ran on a fresh PostgreSQL 17 only.
  • Not in this ticket. The tools agents will call to reach this layer, joins across tables, hidden columns and per-document permissions are later tickets.

Azure note

On Azure's managed PostgreSQL (Flexible Server), the administrator account can create the reader login and set its time, lock and memory limits. That part is documented.

Whether Azure allows the 256 MB temporary-disk cap to be set on one login is not documented. Connapse tries. If Azure refuses, Connapse logs a warning asking the operator to set the server-wide setting temp_file_limit instead. Everything else still works.

Two more things for an Azure operator: don't enable the add-ons that reach other servers (dblink, postgres_fdw), and never add the reader to Azure's admin group. None of this has been run against a live Azure server yet.
