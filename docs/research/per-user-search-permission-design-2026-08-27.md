# Designing per-user search permission filtering: OIDC sign-in, AWS provisioning detection, and a permanent per-user connection

**Date:** 2026-08-27
**Status:** Reviewed; central claim confirmed by experiment against a live AWS account 2026-08-27
**Built on:** no prior corpus material (Connapse MCP tools were not available in this session)

## Executive summary

Connapse's desired shape — admin configures OIDC, Connapse detects the AWS side is provisioned, users link once and permanently — is achievable, and the recommended architecture is: **the customer runs an Amazon Cognito user pool in their own AWS account as the trusted token issuer, federated back to IAM Identity Center over SAML.** Connapse becomes an OIDC client of that Cognito pool. This needs no third-party identity provider, no second user directory, and costs roughly $2 a month for a 200-person deployment — see "An OIDC provider is required, but the customer can host it themselves" below.

Four findings shape the rest. First, **an OIDC provider genuinely is required** — established from the documentation and then confirmed by experiment against a live account (see "What the spike settled" below): AWS states that customer-managed applications "must obtain a token from a trusted token issuer, which is external to IAM Identity Center", and the device authorization flow Connapse already ships structurally cannot reach an identity-enhanced session. Cognito satisfies that requirement from inside the customer's own account, which is why the dependency is not fatal. Second, **permanence cannot come from AWS** — every AWS-side session is bounded and there is no sanctioned durable AWS credential for an absent user — so the durable credential must be the identity provider's refresh token, and the AWS session must be rebuilt from scratch on each resolution rather than extended. Third, **that rebuild must happen per exchange, not per cache window**: Identity Center rejects a token it has already exchanged, so every resolution needs a freshly minted identity-provider token. Fourth, **the join key is not the OIDC subject**: AWS restricts trusted-token-issuer attribute mapping to user name, email, and external ID, so the opaque `sub` claim that would be the natural identifier cannot be used.

A cheaper tier was investigated and **is not recommended**. `ListCallerAccessGrants` does accept ordinary IAM credentials, so the device flow Connapse already ships could in principle reach filtering at *permission-set* granularity with no identity provider. But the device flow itself sees nothing about documents — it supplies only which role to ask as — and the grants it would read must already exist, written by the customer against their `AWSReservedSSO_*` role ARNs. Since Connapse will not create grants on a customer's behalf, that is a configuration almost no deployment will have, and it buys granularity Connapse is not aiming for. The finding is recorded below for completeness rather than as a recommendation.

The largest UX finding is that the integrations page as imagined is off-precedent: no comparable enterprise search product (Amazon Q Business, Kendra, Azure AI Search, Glean, Coveo, Elastic) asks an end user to link a cloud account for search. Identity is derived from SSO sign-in. Connapse has one legitimate reason to keep a lighter version of the page — obtaining `offline_access` consent so background agent runs can resolve a user's permissions when that user is absent.

Two findings are actionable against code already merged. S3 returns grant scopes in at least four shapes, including a bucket-level `s3://bucket*` with **no separating slash**, so naive conversion to a `LIKE` prefix matches `s3://bucket-secrets/` too. And every document indexed before migration `20260827062208_AddDocumentResourceUri` has a null `resource_uri`, which both enforcement predicates treat as denied — so enabling filtering makes the entire pre-existing corpus silently invisible unless a re-sync runs first.

## Research brief

**Question:** What is the best design for Connapse's per-user search permission filtering, given a desired state where an admin configures OIDC sign-in on the provider page, Connapse detects that the customer's AWS account is provisioned for trusted identity propagation, and individual users then establish a permanent connection from an integrations page?

**Sub-questions investigated:**
1. Can Connapse hold a durable, storable credential that mints a fresh AWS identity-enhanced session for a specific user, repeatedly, without that user present?
2. What must exist in the customer's AWS account, and which read-only calls detect each piece?
3. What can an ASP.NET Core OIDC relying party durably hold, and what does a stored refresh token actually yield?
4. How do comparable products model permission filtering and per-user account linking?
5. Where does the primary design fail, and what is the fallback ladder?
6. (Added mid-research) Can IAM Identity Center itself serve as the identity provider, removing the external identity provider dependency entirely?

**Out of scope:** Azure, deferred until AWS is settled. Write permissions — Connapse has no write surface against a source. Creating native S3 Access Grants on the customer's behalf, explicitly rejected by the product owner. Any stored shadow copy of cloud permissions.

**Success criteria:** A recommended architecture with an honest tier ladder, a defensible answer to the permanence question, and concrete detection calls for the provider page.

## Findings by sub-question

### An external OIDC provider is required for per-user granularity — the device flow cannot substitute

This is the finding that decides the shape of the whole design, and it contradicts the hope that Connapse's existing AWS sign-in could be extended. AWS states plainly that "To access an AWS service, customer managed applications must obtain a token from a trusted token issuer, **which is external to IAM Identity Center**" ([customer-managed app setup](https://docs.aws.amazon.com/singlesignon/latest/userguide/trustedidentitypropagation-using-customermanagedapps-setup.html)), and the console wizard makes the trusted token issuer mandatory ([OAuth 2.0 setup](https://docs.aws.amazon.com/singlesignon/latest/userguide/customermanagedapps-trusted-identity-propagation-set-up-your-own-app-OAuth2.html)).

Two independent mechanisms close the device-flow path. `PutApplicationGrant` accepts exactly four grant types — `authorization_code`, `refresh_token`, `urn:ietf:params:oauth:grant-type:jwt-bearer`, `urn:ietf:params:oauth:grant-type:token-exchange` — and `device_code` is not among them ([PutApplicationGrant](https://docs.aws.amazon.com/singlesignon/latest/APIReference/API_PutApplicationGrant.html)). And the plain `sso-oidc:CreateToken` operation that the device flow polls returns only `accessToken`, `expiresIn`, `idToken`, `refreshToken`, `tokenType` — there is no `awsAdditionalDetails` field at all, and its `idToken` "is not implemented or supported" ([CreateToken](https://docs.aws.amazon.com/singlesignon/latest/OIDCAPIReference/API_CreateToken.html)). Since the context assertion "is obtained from the `idToken` claim received in response to a request to SSO OIDC to `CreateTokenWithIAM`" ([identity-enhanced sessions](https://docs.aws.amazon.com/singlesignon/latest/userguide/trustedidentitypropagation-identity-enhanced-iam-role-sessions.html)), the device flow's token can never carry an identity context.

A third quote that looks like corroboration should not be used as such. "OAuth 2.0 grant flows are only available through AWS managed applications that support the flows" sits inside a section about **public clients** — the AWS CLI, toolkits and SDKs registering via `RegisterClient` to retrieve credentials from the access portal ([SAML and OAuth concepts](https://docs.aws.amazon.com/singlesignon/latest/userguide/customermanagedapps-saml2-oauth2.html)). It describes the portal sign-in experience, not whether a customer-managed application may use a grant type; read as this report first read it, it would also forbid the jwt-bearer application the report goes on to recommend.

**Sub-question 6 was settled by experiment, not by documentation.** The two undocumented paths that could have removed the external-provider dependency were both driven against a live AWS account, and both are closed. Details follow.

### What the spike settled

Run against a real IAM Identity Center instance (organization instance, `us-west-1`, caller holding `AdministratorAccess`) on 2026-08-27. Everything it created was deleted afterwards.

**What worked, and is worth knowing.** `PutApplicationGrant` accepts `{"TokenExchange":{}}` — the token-exchange grant takes no configuration, unlike `JwtBearer`. `PutApplicationAuthenticationMethod` accepts an `Iam.ActorPolicy` naming a principal, an action of `sso-oauth:CreateTokenWithIAM`, and `"Resource": "*"`. And `RegisterClient` accepts `--entitled-application-arn` pointing at a *customer-managed* application without complaint.

**Path 1 — exchange a device-flow token. Closed, on two independent grounds.** A public client cannot obtain a token scoped to a customer-managed application: requesting `s3:access_grants:read_write`, `sts:identity_context` or `openid` is accepted by `RegisterClient` but rejected at the authorization page with `invalid_scope`. Only portal scopes such as `sso:account:access` authorize. And a portal-scoped token, submitted to `CreateTokenWithIAM` under the token-exchange grant, fails with `InvalidRequestException` — notably *not* `InvalidGrantException`, which is what a deliberately corrupted token returns, and not `InvalidClientException`, which is what a wrong application ARN returns. The token is recognised and valid; it simply does not name the application as a target audience, and there is no scope string that would make it do so. This is exactly the constraint the API reference states: the subject token "must have authorized scopes that indicate the requested application as a target audience."

**Path 2 — authorization code with PKCE. Closed outright.** `PutApplicationGrant` with `--grant-type authorization_code` returns `ValidationException: Grant type: authorization_code not supported`, even though `authorization_code` is listed among that parameter's valid values in the [API reference](https://docs.aws.amazon.com/singlesignon/latest/APIReference/API_PutApplicationGrant.html). The documented valid-values list is wider than what the service accepts for customer-managed applications. Corroborating this, `RegisterClient` returns no `authorizationEndpoint` field at all, despite one appearing in its documented response shape — so there is no authorize endpoint to redirect a browser to.

`entitledApplicationArn` is therefore a mechanism for public clients to reach **AWS-managed** applications, not a bridge to customer-managed ones. The jwt-bearer grant with a trusted token issuer is the only entry point into trusted identity propagation for an application like Connapse. Confidence: high, and now empirical rather than inferential.

What this does *not* establish is that the token issuer must belong to a third party — only that one must exist and be publicly reachable by AWS. The next section covers who can host it.

### An OIDC provider is required, but the customer can host it themselves

Amazon Cognito is an OIDC provider, runs in the customer's own AWS account, and publishes a discovery endpoint and RS256 JWKS that Identity Center can reach — the three requirements Connapse itself fails. AWS documents the integration end to end in [How to implement trusted identity propagation for applications protected by Amazon Cognito](https://aws.amazon.com/blogs/security/how-to-implement-trusted-identity-propagation-for-applications-protected-by-amazon-cognito/), and the pattern is confirmed independently by AWS's guidance that "the trusted token issuers feature is completely independent from the authentication feature of IAM Identity Center and doesn't need to be the same identity provider as is used for authenticating into IAM Identity Center."

The user pool federates back to Identity Center over SAML, so Identity Center stays the only directory: users authenticate with their existing Identity Center credentials, and Cognito provisions matching profiles automatically on first federated sign-in. The AWS resources involved are a Cognito user pool, a user pool domain, a user pool app client, an Identity Center trusted token issuer, an Identity Center customer-managed OAuth application, and an Identity Center SAML application — on top of the S3 Access Grants instance, location and grants covered in the provisioning section.

Cognito's cost for this population is small: SAML and OIDC federated users have a free tier of 50 monthly active users per account, and $0.015 per MAU beyond it ([pricing](https://aws.amazon.com/cognito/pricing/)).

The one adoption constraint is the callback URL. Cognito "requires `HTTPS` over `HTTP` except for `http://localhost` for testing purposes only" ([app client settings](https://docs.aws.amazon.com/cognito/latest/developerguide/cognito-user-pools-app-idp-settings.html)), so a deployment served at a plain-HTTP LAN address has no valid redirect URI and needs either TLS or a localhost-completed sign-in. Confidence: high on the architecture, untested end to end — no spike has yet driven this chain.

### Permission-set granularity is technically reachable without an identity provider, and still not worth building

`ListCallerAccessGrants` explicitly accepts plain IAM credentials: "The caller (grantee) can be an AWS Identity and Access Management (IAM) identity **or** AWS Identity Center corporate directory identity", and it requires only the `s3:ListCallerAccessGrants` permission ([API reference](https://docs.aws.amazon.com/AmazonS3/latest/API/API_control_ListCallerAccessGrants.html)). S3 Access Grants supports IAM users and roles as grantees alongside directory users and groups, with `GranteeIdentifier` being a role or user ARN ([create grants](https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-grants-grant-create.html)). Connapse's existing device flow already reaches `sso:GetRoleCredentials`, which "Returns the STS short-term credentials for a given role name that is assigned to the user" ([GetRoleCredentials](https://docs.aws.amazon.com/singlesignon/latest/PortalAPIReference/API_GetRoleCredentials.html)).

Note what the device flow contributes here, because it is easy to overstate: nothing about documents. It reports which AWS accounts a user can reach and which permission set they hold. All document-level knowledge comes from Access Grants, a separate opt-in system, read through role credentials the device flow merely helps select.

**The unverified step is principal resolution.** `GetRoleCredentials` returns credentials for an assumed-role *session* (`arn:aws:sts::…:assumed-role/AWSReservedSSO_<PermissionSet>_<hash>/user@example.com`), whereas a grant is written against the *base* role ARN (`arn:aws:iam::…:role/aws-reserved/sso.amazonaws.com/AWSReservedSSO_<PermissionSet>_<hash>`). Whether Access Grants resolves the session principal back to the base role is nowhere documented. If it does not, this path returns an empty list for every user.

Three further constraints sink the tier even if that resolves favourably. It only helps customers who *already* wrote grants against their `AWSReservedSSO_*` role ARNs — ARNs carrying a generated hash suffix that changes when a permission set is reprovisioned — and the product owner has ruled out Connapse creating grants on their behalf, so the addressable population is a narrow and brittle slice rather than "organizations that use permission sets". A user assigned three permission sets across five accounts has fifteen candidate role identities, and `GetRoleCredentials` takes one `accountId` and `roleName` per call, so Connapse must either pick one or union them; unioning grants the user the maximum of their permission sets simultaneously, which no single AWS session would ever hold, and that is a security decision rather than an implementation detail. And grants returned to an IAM-role caller carry `ApplicationArn: "NA"`, so a client-side filter keeping only the caller's application ARN or `ALL` would discard exactly the grants this path depends on — the server-side `allowedByApplication` request parameter is the correct control, and that detail carries over to the per-user design regardless.

**Verdict: do not build this.** It delivers permission-set granularity, which is not the goal, on top of a configuration almost no deployment will have, gated behind an undocumented resolution question. Confidence: high on the API surface, unresolved on principal resolution, and the resolution no longer matters.

### Permanence must live at the identity provider, not at AWS

AWS bounds every session it issues. The customer-managed application's refresh token grant "refreshes the access token for the session every 60 minutes, **until the session expires or the user ends the session**" ([OAuth 2.0 setup](https://docs.aws.amazon.com/singlesignon/latest/userguide/customermanagedapps-trusted-identity-propagation-set-up-your-own-app-OAuth2.html)). *Which* session that is, is less clear than it first appears: AWS defines user interactive sessions — default 8 hours, configurable from 15 minutes to 90 days — as "sessions tied to a user's sign-in to the AWS access portal or access to AWS managed applications" ([user interactive sessions](https://docs.aws.amazon.com/singlesignon/latest/userguide/user-interactive-sessions.html)), and in the jwt-bearer flow the user never signs into the portal at all. Treat the 8-hour/90-day figures as the nearest documented bound rather than a confirmed cap on this path.

What is not ambiguous is that the one AWS feature designed to outlive a session — user background sessions — is affirmatively denied here on two counts: "A customer managed application can't create a user background session", and it is "not supported for automated, scheduled workflows" ([background sessions](https://docs.aws.amazon.com/singlesignon/latest/userguide/user-background-sessions.html)). There is no sanctioned durable AWS credential for an absent user, whatever the exact session bound turns out to be.

The durable credential is therefore the identity provider's refresh token, and the AWS session is rebuilt from scratch on each resolution rather than extended — which sidesteps the 90-day cap entirely. Refresh token durability by provider: Okta issues unlimited-lifetime refresh tokens that expire only after 7 days unused ([Okta](https://developer.okta.com/docs/guides/refresh-tokens/main/)); Entra ID's have no specified lifetime, with a documented 90-day inactivity window and an "until-revoked" maximum, no longer configurable since January 2021 ([configurable token lifetimes](https://learn.microsoft.com/en-us/entra/identity-platform/configurable-token-lifetimes)); Auth0 supports absolute lifetimes up to one year, or non-expiring for non-SPA clients ([Auth0](https://auth0.com/docs/secure/tokens/refresh-tokens/configure-refresh-token-expiration)); Keycloak offline tokens "never expire" and are exempt from SSO session timeouts ([Keycloak admin guide](https://www.keycloak.org/docs/latest/server_admin/index.html)).

**Idle expiry is the only real permanence risk**, and it is fixable: a background job that exercises each stored refresh token weekly keeps Okta's 7-day and Entra's 90-day inactivity clocks from ever firing. Confidence: high.

### The token-exchange contract: audience is easy, subject and single-use are not

**Audience is a non-problem.** OpenID Connect Core §12.2 says a refresh response "might not contain an `id_token`", and that if one is returned "its `aud` Claim Value MUST be the same as in the ID Token issued when the original authentication occurred" ([OIDC Core](https://openid.net/specs/openid-connect-core-1_0.txt)); every major provider pins the audience to the client that signed the user in ([Entra](https://learn.microsoft.com/en-us/entra/identity-platform/id-token-claims-reference), [Okta](https://developer.okta.com/docs/guides/validate-id-tokens/main/)). But the AWS side is what adapts: `PutApplicationGrant` takes `JwtBearer.AuthorizedTokenIssuers[{TrustedTokenIssuerArn, AuthorizedAudiences}]`, and AWS's own worked example sets `AuthorizedAudiences` to the application's own identity-provider client ID ([directory identities](https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-grants-directory-ids.html)). **No second OIDC client and no second consent are needed.** The Keycloak ID-token caveat also matters less than it first appeared, because AWS accepts either token type: "The token can be an identity token or an access token" ([using apps with a trusted token issuer](https://docs.aws.amazon.com/singlesignon/latest/userguide/using-apps-with-trusted-token-issuer.html)).

**The subject claim is the real constraint, and it rules out the obvious design.** AWS restricts `IdentityStoreAttributePath` to exactly three attributes — "user name, email, and external ID" — and its example maps `ClaimAttributePath: preferred_username` to `IdentityStoreAttributePath: userName` ([trusted token issuer configuration](https://docs.aws.amazon.com/singlesignon/latest/userguide/trusted-token-issuer-configuration-settings.html)). An Okta or Entra `sub` is an opaque provider GUID that will match none of them. So Connapse cannot key on the OIDC subject; it must carry `email` or `preferred_username` into the exchange, which makes an email address a join key into an authorization decision and brings the account-takeover considerations that implies. Any identity-provider configuration where a user can change their own email or where aliases resolve loosely needs review before this ships.

**Every exchange consumes its token.** "If IAM Identity Center receives a request to exchange a token that IAM Identity Center has already exchanged, the request fails" ([using apps with a trusted token issuer](https://docs.aws.amazon.com/singlesignon/latest/userguide/using-apps-with-trusted-token-issuer.html)), and both Okta and Entra commonly emit a `jti`. A token therefore cannot be reused across a retry, across two concurrent searches, or across a cache window — each resolution must mint a fresh provider token from the stored refresh token. That is an extra round trip per resolution and it interacts directly with refresh-token rotation, since a rotating provider hands back a new refresh token on every mint that must be persisted before the next one is attempted.

Two further requirements are easy to miss: the trusted token issuer requires **RS256** signing, and "Using a custom signing key for JWTs from Microsoft Entra ID is not supported" (same page). Confidence: high.

### Per-user account linking is off-precedent for search, and the industry uses early binding

Across every documented comparable product, the end user's identity is derived from SSO sign-in and the admin configures the connector once. Azure AI Search attaches the caller's Entra token as `x-ms-query-source-authorization` and filters on `oid` and group claims, with no linking step in the flow ([query-time enforcement](https://learn.microsoft.com/en-us/azure/search/search-query-access-control-rbac-enforcement)). Amazon Q Business crawls each source's ACLs and directory into an internal User Store, an admin-side construct ([User Store](https://docs.aws.amazon.com/amazonq/latest/qbusiness-ug/principal-store-hiw.html)). Glean, Kendra, Coveo and Elastic follow the same shape. The instructive counter-example is that Q Business *does* use per-user OAuth — but only for **plugins** that take actions, not for search ([custom plugin prerequisites](https://docs.aws.amazon.com/amazonq/latest/qbusiness-ug/custom-plugin-prereqs.html)). The category line is: read and search derive identity from SSO; act-as-me uses per-user OAuth.

The same products are overwhelmingly **early binding** — access control lists indexed alongside documents and refreshed by a crawler. Coveo describes "early-binding permission retrieval… at crawling time" ([Coveo](https://docs.coveo.com/en/1719/)); Azure states "Permission changes in the source system are only reflected after that metadata is synchronized to the index" ([document-level access](https://learn.microsoft.com/en-us/azure/search/search-document-level-access-overview)); Elastic writes a hidden `.search-acl-filter-*` index ([Elastic document-level security](https://www.elastic.co/docs/reference/search-connectors/es-dls-overview)). Connapse's query-time resolution is genuinely off-precedent; the freshness argument for it is real, and both AWS and Azure admit staleness in writing.

On failure behavior the industry has moved toward failing closed. Kendra fails open by design — "If this information is not included in the query, Amazon Kendra returns all documents" — and warns that user context filtering "isn't an authentication or authorization control" ([Kendra](https://docs.aws.amazon.com/kendra/latest/dg/user-context-filter.html)). Azure AI Search changed to fail closed in November 2025, and on evaluation failure "returns 5xx and does not return a partially filtered result set" ([Azure](https://learn.microsoft.com/en-us/azure/search/search-query-access-control-rbac-enforcement)). Confidence: high.

### The Access Grants coverage gap, and a grant-scope format that is a live bug

`ListCallerAccessGrants` returns only "the caller's access grants that were created using S3 Access Grants" ([API reference](https://docs.aws.amazon.com/AmazonS3/latest/API/API_control_ListCallerAccessGrants.html)). AWS positions IAM and bucket policies as the default — "The simplest approach for managing access to small-to-medium numbers of datasets… is to define IAM permission policies and S3 bucket policies" — with Access Grants offered "instead of using these approaches" ([overview](https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-grants.html)). For an IAM-policy-managed customer the call succeeds and returns an empty list, **indistinguishable from "this user may read nothing"** unless Connapse separately checks whether an Access Grants instance exists.

No other AWS API closes the gap. `iam:SimulatePrincipalPolicy` is a decision oracle rather than an enumerator — it requires the `ResourceArns` you are trying to discover, does not simulate resource-based policies for roles, cannot take an assumed-role or federated ARN as `CallerArn`, and AWS warns that results "can differ from your live AWS environment" ([API reference](https://docs.aws.amazon.com/IAM/latest/APIReference/API_SimulatePrincipalPolicy.html)). IAM Access Analyzer is bucket-level and scan-based ([findings](https://docs.aws.amazon.com/IAM/latest/UserGuide/access-analyzer-findings.html)).

The format detail matters for code already merged, and AWS documents it inconsistently enough that a parser must handle several shapes. The [list grants](https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-grants-list-grants.html) page shows a whole-bucket scope as **`s3://amzn-s3-demo-bucket*` — an asterisk with no separating slash**, while the [create grants](https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-grants-grant-create.html) page documents the same thing as `s3://{{bucket}}/*` *with* the slash, and shows one `S3SubPrefix` value producing `s3://amzn-s3-demo-bucket/prefix*` in its CLI example and `s3://amzn-s3-demo-bucket/prefixB` — no asterisk at all — in its Java example on the same page. At minimum the parser must accept `s3://bucket*`, `s3://bucket/*`, `s3://bucket/prefix*`, and trailing forms with no asterisk.

The slashless bucket form is the dangerous one: stripping the `*` and matching `LIKE 's3://amzn-s3-demo-bucket%'` also matches `s3://amzn-s3-demo-bucket-secrets/`, a cross-bucket leak. Normalizing it to `s3://amzn-s3-demo-bucket/` is the right direction and still prefix-matches objects at the bucket root, but it is a rule to apply across all four shapes rather than a patch for one literal. Grants can also target a single object ([grants](https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-grants-grant.html)), which must be matched by equality or `report.pdf` silently grants `report.pdf.bak`. Responses also carry `Permission` (READ, WRITE or READWRITE), which should be filtered to READ and READWRITE. Confidence: high on the shapes observed, low that four is the complete set.

### Query-time resolution will not survive without a short cache, and AWS caches this itself

STS allows 600 requests per second per account per Region, shared across `AssumeRole`, `GetCallerIdentity` and others ([IAM quotas](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_iam-quotas.html)) — that is the whole account's budget, not search's share of it. No transactions-per-second figure is published for `ssooidc` token operations or s3control access-grants operations, which makes undocumented throttling on a hot path undesignable.

The chain is longer than three calls, because **`ListCallerAccessGrants` is scoped to one grantor account and one Region per call.** It requires an `x-amz-account-id` header naming "the AWS account ID of the S3 Access Grants instance", and only one instance may exist per Region per account ([limitations](https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-grants-limitations.html)). A Connapse deployment indexing buckets across three accounts in two Regions must fan out across every (account, Region) pair it holds sources for, then union and paginate the results. Mint plus exchange plus assume-role is four sequential round trips before that fan-out even begins, so a single-pair deployment is roughly 200–600ms and a multi-account one is materially worse — and the throttling exposure multiplies with the fan-out.

The freshness objection to caching is weaker than it appears, because AWS caches this itself. AWS's own S3 Access Grants Java plugin holds a 30,000-entry credentials cache with a time-to-live of 90% of the `GetDataAccess` duration — about 54 minutes at the 1-hour default — plus a 3,000-entry access-denied cache at 5 minutes ([plugin cache documentation](https://github.com/aws/aws-s3-accessgrants-plugin-java-v2/blob/main/README_CACHE.md)). Vended credentials themselves are valid 900–43,200 seconds ([GetDataAccess](https://docs.aws.amazon.com/AmazonS3/latest/API/API_control_GetDataAccess.html)), so even the "live" path freezes an authorization decision for up to 12 hours. Zero staleness does not exist; only the window is negotiable. For comparison, API Gateway's Lambda authorizer cache defaults to 300 seconds ([CreateAuthorizer](https://docs.aws.amazon.com/apigateway/latest/api/API_CreateAuthorizer.html)), and Zanzibar serves normal checks from bounded-staleness caches ([zookies](https://authzed.com/blog/zedtokens)). **A 60-second time-to-live on the resolved prefix set is roughly 5× fresher than API Gateway's default and 50× fresher than AWS's own plugin** — a defensible number rather than an arbitrary one. Confidence: high.

### Provisioning detection: what to create, what to check, and what has no CloudFormation

The ordered create-list and its matching detection call:

| # | Create | Detect |
|---|---|---|
| 1 | Identity Center instance, same Region as the Access Grants instance | `sso-admin:ListInstances` |
| 2 | Users and groups provisioned by SCIM | `identitystore:ListUsers` / `ListGroups` |
| 3 | `sso-admin:CreateTrustedTokenIssuer` (`OIDC_JWT`) | `ListTrustedTokenIssuers` then `DescribeTrustedTokenIssuer` — verify `IssuerUrl`, `ClaimAttributePath`, `IdentityStoreAttributePath` |
| 4 | `sso-admin:CreateApplication` (`applicationProvider/custom`) | `ListApplications` then `DescribeApplication` (`Status=ENABLED`) |
| 5 | `sso-admin:PutApplicationGrant` (jwt-bearer, with `AuthorizedAudiences`) | `ListApplicationGrants` then `GetApplicationGrant` — verify the issuer ARN and that the audience matches Connapse's client ID |
| 6 | `sso-admin:PutApplicationAccessScope --scope s3:access_grants:read_write` | `ListApplicationAccessScopes` |
| 7 | `sso-admin:PutApplicationAuthenticationMethod --type IAM`, allowing Connapse's role `sso-oauth:CreateTokenWithIAM` | `GetApplicationAuthenticationMethod`, then parse the policy for the role ARN |
| 8 | `s3control:CreateAccessGrantsInstance` | `GetAccessGrantsInstance` |
| 9 | `s3control:AssociateAccessGrantsIdentityCenter` | Same call: `IdentityCenterInstanceArn` non-null and equal to step 1 |
| 10 | `s3control:CreateAccessGrantsLocation` plus its location role | `ListAccessGrantsLocations` |
| 11 | `s3control:CreateAccessGrant` | `ListAccessGrants` |

`sts:identity_context` is **not** a scope you configure — it is returned automatically in the exchanged token's scope array ([directory identities](https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-grants-directory-ids.html)). The location role's trust policy must permit `sts:SetContext` with `sts:RequestContextProviders` set to `arn:aws:iam::aws:contextProvider/IdentityCenter`; omitting it is a silent trusted-identity-propagation failure ([tutorial](https://docs.aws.amazon.com/singlesignon/latest/userguide/tip-tutorial-s3.html)).

**The strongest single health check** is `GetAccessGrantsInstance` returning an `IdentityCenterInstanceArn` equal to the one from `ListInstances` — that one comparison collapses steps 1, 8 and 9 into a green or red state, and the `sso-admin` Get operations then narrow amber to a specific missing piece.

Two adoption constraints deserve emphasis. **There is no CloudFormation coverage for the trusted token issuer, grants, access scopes, or authentication method.** `AWS::SSO::Application` exposes only `ApplicationProviderArn`, `InstanceArn`, `Name`, `PortalOptions`, `Status` and `Tags` ([resource reference](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-sso-application.html)), and no `AWS::SSO::TrustedTokenIssuer` type exists ([AWS::SSO resource list](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/AWS_SSO.html)). Steps 3, 5, 6 and 7 must be a command-line script; steps 8 through 11 can be a CloudFormation stack. And with an **organization instance**, the Identity Center instance "must always reside in the management account" ([delegated administration](https://docs.aws.amazon.com/singlesignon/latest/userguide/delegated-admin.html)), so those `sso-admin` writes must run in the management or delegated-admin account. **Account instances do support trusted identity propagation** and OAuth 2.0 customer-managed applications ([instances](https://docs.aws.amazon.com/singlesignon/latest/userguide/identity-center-instances.html)), but require every participating service to live in the same account ([prerequisites](https://docs.aws.amazon.com/singlesignon/latest/userguide/trustedidentitypropagation-overall-prerequisites.html)) and cannot replicate across Regions — so multi-Region buckets are effectively organization-instance-only. Confidence: high.

## Recommended design

**There are two destinations, not three.** Today's unrestricted, clearly-labelled behaviour, and per-user filtering. The permission-set tier examined above is a dead end and should not be scheduled.

**Per-user filtering needs an OIDC provider, but not a third-party one — the customer can stand one up inside their own AWS account.** Amazon Cognito is an OIDC provider with a publicly reachable discovery endpoint and RS256 keys, which is precisely the requirement Connapse itself cannot meet, and AWS documents this exact integration ([How to implement trusted identity propagation for applications protected by Amazon Cognito](https://aws.amazon.com/blogs/security/how-to-implement-trusted-identity-propagation-for-applications-protected-by-amazon-cognito/)). This removes the Okta-or-Entra dependency that would otherwise have made the feature unreachable for a self-hosted audience.

**Crucially, it does not create a second user directory.** The Cognito user pool federates back to IAM Identity Center over SAML, so people authenticate with their Identity Center credentials and Cognito provisions a matching profile automatically on first federated sign-in — "the Cognito user pool will automatically create user profiles". Identity Center remains the single source of user identity. The claim mapping is `ClaimAttributePath=email` to `IdentityStoreAttributePath=emails.value`, which satisfies the constraint that the subject may only be user name, email, or external ID.

The sequence: Connapse redirects the user to Cognito; Cognito redirects to Identity Center; Cognito parses the SAML assertion and returns a JWT; Connapse exchanges that JWT at `CreateTokenWithIAM` under the jwt-bearer grant; the resulting identity context drives `AssumeRole` with `ProvidedContexts`; and `ListCallerAccessGrants` then answers for that individual person.

**Cost is not a barrier.** Users who sign in through SAML or OIDC federation get 50 monthly active users free per account, then $0.015 per MAU ([Cognito pricing](https://aws.amazon.com/cognito/pricing/)). A 200-person deployment pays roughly $2.25 per month.

**One deployment constraint does need designing around.** Cognito "requires `HTTPS` over `HTTP` except for `http://localhost` for testing purposes only" as a callback URL ([app client settings](https://docs.aws.amazon.com/cognito/latest/developerguide/cognito-user-pools-app-idp-settings.html)). A Connapse instance reached at `http://192.168.1.50:5001` cannot register that address as a redirect URI. Deployments therefore need either a TLS certificate or a sign-in flow that completes against `http://localhost` on the operator's own machine. This is the sharpest remaining adoption question and should be settled before the provider page is designed.

Connapse still has to become an OIDC relying party — that work does not disappear, it simply points at Cognito instead of Okta. What changes is the customer prerequisite: from "already own an identity provider" to "run the setup we generate for you", which is a prerequisite a self-hosted AWS user can actually satisfy.

**The shared work is unaffected either way.** Grant-scope parsing, the prefix predicate, the failure-state taxonomy, the null-principal rule and the `resource_uri` backfill are identical whichever destination wins, and none of them wait on this decision.

**Make sign-in the link, and keep the integrations page for consent and status.** Since per-user filtering requires federating sign-in to the customer's identity provider, sign-in already establishes who the user is; no comparable product asks for a separate connection. The one thing the integrations page should genuinely collect is **`offline_access` consent**, which is what allows a background agent run to resolve a user's permissions while that user is absent. Framing it as an explicit opt-in rather than folding it into sign-in is the better privacy posture — it means Connapse only holds a durable token for users who chose to grant one. Two things must be surfaced honestly on that consent screen: the only documented access scope is `s3:access_grants:read_write`, so a search-only product is asking for a write-capable scope; and the claim Connapse persists as the join key is the user's email or `preferred_username`, not an opaque identifier.

**Achieve permanence at the identity provider layer, and build a real token store.** ASP.NET Core has no server-side token store — `SaveTokens = true` puts tokens in the authentication cookie, and a background agent run has no `HttpContext` to read a cookie from. Connapse must persist refresh tokens in its own table, encrypted with Data Protection, with the key ring persisted outside the container: in Docker the keys "should be maintained in either… a Docker volume that persists beyond the container's lifetime" or an external provider, or every stored token becomes undecryptable on restart ([Data Protection configuration](https://learn.microsoft.com/en-us/aspnet/core/security/data-protection/configuration/overview)). On each resolution: mint a fresh provider token from the stored refresh token (persisting the rotated refresh token before proceeding), then `CreateTokenWithIAM` with the jwt-bearer grant, then `AssumeRole` with `ProvidedContexts`, then `ListCallerAccessGrants` once per (account, Region) pair. Never store an AWS refresh token; rebuild the AWS session each time. Add a weekly background touch job so idle-expiry clocks never fire, which is what turns "long-lived" into "permanent in practice".

**Cache the resolved prefix set for 60 seconds per user, and cache errors separately and briefly.** Delete the existing inverted 15-minute-allow and 5-minute-deny values on `CloudScopeService` while doing so. Errors need their own short window — a few seconds — because not caching them means one three-to-N-call chain per search per user against exactly the undocumented throttling this report could not model, while caching them at 60 seconds locks a user out for a full minute on one transient failure. On revocation, Identity Center kills existing application sessions "within 30 minutes… at their next refresh attempt" ([authentication concepts](https://docs.aws.amazon.com/singlesignon/latest/userguide/authconcept.html)); set the assumed role's maximum session duration to one hour so the outstanding-credential window stays small.

**Fail closed, but distinguish four states rather than two.** XACML 3.0 §7.2.2 is the standard formulation — "A deny-biased PEP denies access unless it receives an explicit Permit decision" ([specification](http://docs.oasis-open.org/xacml/3.0/xacml-3.0-core-spec-os-en.html)). Connapse needs to separate *filtering not configured* (`SearchScopes.Unrestricted`, as today); *resolver errored* (fail closed with a distinguishable error); *resolver returned zero grants* (expected wherever no Access Grants instance exists — a configuration message, not a denial); and *the document predates filtering* (a null `resource_uri`, which is a re-sync prompt, not a permission decision). Collapsing any of the last three into plain denial turns a configuration problem into an unending support load.

**Decide the null-principal rule before shipping, not after.** `ISearchScopeResolver.ResolveAsync` takes a nullable user id, documented as null "when the caller could not be resolved to a person" — which is the ordinary state for the MCP server and for personal-access-token callers, two of the three access surfaces. `Unrestricted` reopens the hole for anyone holding a token; `None` breaks MCP and every background agent run. The plan's stated intent is deny-by-default once filtering is configured, which means MCP and PAT surfaces need a resolvable principal before filtering can be switched on anywhere.

**Re-sync is remediation, not a prerequisite.** *(Revised 2026-08-27 — this section originally called a full re-sync a precondition for enabling filtering, on the reasoning that both enforcement sites gate on `resource_uri IS NOT NULL` and a null coordinate therefore denies. Manual testing against a real deployment showed what that would mean: 127,892 of 127,898 documents hidden the moment filtering was switched on, because uploads have no external address by design and only the S3 and Azure connectors ever record one. The rule shipped inverted — see the spec.)*

A document with no recorded coordinate is **not governed by cloud permissions** and falls back to Connapse's own access control; filtering narrows only the subset that carries a cloud address. So enabling filtering hides nothing, and no backfill gates it.

What a missing coordinate does cost is filtering itself: a document that came from S3 but has no recorded address is visible to everyone rather than narrowed by grants — a permissive gap, not a destructive one. Phase 2 deliberately declined a SQL backfill because the derivation would be silently wrong for a re-pointed source, so the remedy is a re-sync per source, and the admin UI names which sources are affected. Only sources whose connector can record a coordinate are named; telling an SFTP or filesystem source to re-sync would be advice that cannot work.

**Fix the grant-scope conversion before any resolver ships.** Normalize all four observed bucket and prefix shapes to a trailing-slash form before prefix matching, match object-level scopes by equality rather than prefix, filter `Permission` to READ and READWRITE, and use the server-side `allowedByApplication` request parameter rather than filtering `ApplicationArn` client-side — a client-side filter would discard the `"NA"` grants that an IAM-role caller receives.

## Conflicts and uncertainties

**Whether Access Grants resolves an assumed-role session principal to its base role ARN is undocumented.** `GetRoleCredentials` yields an `arn:aws:sts::…:assumed-role/…` session; grants are written against the base `arn:aws:iam::…:role/aws-reserved/sso.amazonaws.com/…`. No AWS page states whether the two are reconciled. This mattered only to the permission-set path, which is no longer recommended, so it is recorded rather than queued.

**Resolved by experiment: the `authorization_code` path does not exist for customer-managed applications.** It was the report's highest-priority open question and is now closed — `PutApplicationGrant` rejects the grant type outright, and `RegisterClient` returns no authorize endpoint. Two documentation defects are worth recording, because anyone re-deriving this will hit them: `PutApplicationGrant`'s valid-values list includes `authorization_code`, which the service refuses, and `RegisterClient`'s documented response shape includes `authorizationEndpoint` and `tokenEndpoint`, neither of which is actually returned. Reasoning from those API references alone produces a wrong answer, which is what happened on the first pass through this research.

**One AWS sentence, read literally, would undercut per-user filtering altogether.** The list-grants page says: "For corporate directory identities, when listing the caller's access grants, S3 Access Grants returns the grants of the IAM identity that is used for the identity-aware session" ([list grants](https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-grants-list-grants.html)). Read strictly, that returns the *bearer role's* grants rather than the *user's*, which is the opposite of what trusted identity propagation exists to do. It is most likely loose wording, but it should be resolved by observation during the first end-to-end test rather than assumed away.

**The AWS security blog's mention of "refresh tokens if available" refers to the Okta refresh token in its sample, not an Identity Center one.** It should not be read as evidence that Identity Center issues durable refresh tokens. Separately, AWS's own jwt-bearer example *does* show `CreateTokenWithIAM` returning a `refreshToken` with `issuedTokenType: urn:ietf:params:oauth:token-type:refresh_token` ([directory identities](https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-grants-directory-ids.html)) — so an AWS refresh token exists on this path even though the recommended design deliberately does not store one.

**Refresh token rotation behavior on Identity Center is undocumented in both directions** — the documentation neither confirms nor denies it.

**This report's UX recommendation conflicts with the stated desired state.** The product owner asked for an integrations page where users connect accounts; the precedent research finds no comparable search product does this. The recommendation narrows rather than removes the page, but the disagreement is real and is the owner's to settle.

## Gaps — what we did not find

- No published transactions-per-second quota for `ssooidc` token operations or for s3control access-grants operations. Throttling behavior on a hot path is therefore unmodellable without measurement.
- No documented per-caller limit on the number of access grants `ListCallerAccessGrants` can return, only the 100,000-per-instance quota — so pagination depth for a heavily-grouped user is unknown.
- No measured end-to-end latency for the token-exchange chain; the 200–600ms figure is an estimate from four sequential round trips plus a per-account fan-out, not a benchmark.
- No rule found, in AWS documentation or elsewhere, for which permission set to use when a user holds several. Whether to pick one or union them is a product decision this research cannot settle.
- No documentation on whether an identity-enhanced session's grants are evaluated at `GetDataAccess` time or frozen at session creation.
- Azure's equivalent path was deliberately out of scope and remains unmapped; there is no `IS3Discovery` equivalent for Azure today.
- Enterprise RAG vendors' internal handling of per-user tokens is largely undocumented publicly; the claim that they use service accounts rather than per-user refresh tokens rests on vendor overviews and is weaker than the rest of this report.

## Source quality assessment

Strongly primary. The AWS findings rest almost entirely on `docs.aws.amazon.com` API references and user guides, with several claims quoted verbatim rather than paraphrased; the identity-provider findings rest on the OpenID Connect Core specification, RFC 9700, and first-party Okta, Microsoft, Auth0 and Keycloak documentation. The competitive-precedent findings rest on first-party product documentation from AWS, Microsoft, Coveo, Elastic and Glean. Two areas are weaker and are marked as such in the text: the claim about how enterprise RAG vendors handle per-user tokens internally is inferred from vendor overviews, and the caching time-to-live recommendation synthesizes AWS's own plugin defaults with API Gateway and Zanzibar anchors rather than resting on a single authoritative number.
