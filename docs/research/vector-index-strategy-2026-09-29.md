# What vector-index strategy should Connapse use for per-container (multi-tenant) search on pgvector?
**Date:** 2026-09-29
**Status:** Reviewed
**Built on:** #570 probe result (docs/plans/vector-index-recall-570.md); connapse-cloud-azure-postgres (memory)

## Executive summary
Connapse's search always filters to one container, which the filtered-ANN literature and every dedicated vector database treat as the easy case: search small tenants exactly and give large tenants their own index, never a shared index filtered afterwards. Today Connapse builds exactly the discouraged structure — one IVFFlat index per embedding model shared by all containers, searched with pgvector's default of one probe — but PostgreSQL's planner ignores it and searches each container exactly, which pgvector's maintainer calls the right plan for selective filters. The risk is the future: once the planner does pick the shared index, recall can fall sharply (pgvector's own benchmark shows ~47% recall at probes = 1, and post-filtered searches can return fewer than 30 hits). The evidence points to: keep exact search per container up to tens of thousands of vectors; for larger containers use HNSW with pgvector 0.8 iterative scans (available on Azure's pgvector 0.8.2) or per-container partitions; and never let a shared, post-filtered index serve a small container. The per-container size at which exact search gets too slow in Connapse is unmeasured; published switch points range from ~3k to ~50k vectors.

## Research brief
**Question:** How should Connapse index vectors so container-filtered search keeps full recall and stays fast as containers and databases grow, self-hosted and on Azure Database for PostgreSQL?
**Sub-questions:** (1) pgvector's planner and filtering behaviour and maintainer guidance; (2) Postgres-based platforms and extensions, especially what runs on Azure; (3) how dedicated vector databases handle filtered multi-tenant search; (4) filtered-ANN research, exact-search cost, and how to test recall at scale.
**Out of scope:** changing embedding models; moving off PostgreSQL.
**Success criteria:** a recommended strategy and a test plan to set Connapse's own thresholds.

## pgvector's behaviour and guidance
pgvector's documentation and maintainer describe Connapse's current plan as expected cost-based behaviour, not a bug. The planner picks the cheapest estimated plan among a table scan, a B-tree on the filter column, or the approximate index (Andrew Kane, pgvector issues #301, #259); for a filter matching a small share of rows the README's first recommendation is an index on the filter column, i.e. exact search. Approximate indexes filter after the scan, so with IVFFlat at the default `ivfflat.probes = 1` a filtered query can return fewer than LIMIT rows; Kane's benchmark (#678) shows recall of 46.9% at probes = 1 (55.5% with iterative scan). pgvector 0.8.0 added iterative index scans: `hnsw.iterative_scan` (off / strict_order / relaxed_order; `hnsw.max_scan_tuples` default 20,000; `hnsw.ef_search` default 40) and `ivfflat.iterative_scan` (relaxed_order only; `ivfflat.max_probes`). All default to off. HNSW has a better speed–recall trade-off and needs no training; IVFFlat's lists are trained at build time, so recall degrades as data grows until a REINDEX (Connapse builds its IVFFlat index at startup, possibly on little data). Partial-index predicates only match non-generic plans when the filter is a parameter (PostgreSQL docs; Npgsql's default unprepared statements are custom-planned). For many filter values, pgvector recommends list partitioning over many partial indexes. Azure Database for PostgreSQL flexible server ships pgvector 0.8.2 on PostgreSQL 13–18, so iterative scans are available there.

## Postgres platforms and Azure
No Postgres vector extension that runs on Azure flexible server filters inside the index; the portable option is pgvector 0.8 HNSW with iterative scans. Azure's `pg_diskann` 0.6.5 is allow-listed but on flexible server only post-filters iteratively (`diskann.iterative_search`), the same class of behaviour pgvector 0.8 has; in-index predicate pushdown exists only in Azure HorizonDB (preview), with no published recall figures. Timescale's pgvectorscale (label-filtered StreamingDiskANN) and Google AlloyDB's ScaNN inline filtering are not available on Azure. AWS's pgvector 0.8 study (10M × 384-dim, filters matching 0.5–25% of rows) found post-filtered HNSW returned complete result sets 0–10% of the time on 0.7.4 and 100% with 0.8 iterative scans, with p99 latency falling from 123 ms to 13 ms — but it measured completeness, not recall against exact search. Supabase recommends HNSW over IVFFlat for changing data; Neon reports exact scans fine at ~10k rows (~36 ms) and "costly at 50k". Azure's guidance adds parallel sequential scans (`max_parallel_workers_per_gather`) to speed exact search.

## Dedicated vector databases
Dedicated vector databases converge on one design: exact search for small tenants, a per-tenant index for large ones, switched by the filter's estimated match count. Qdrant recommends one collection with a tenant field, `is_tenant` to store tenants contiguously, per-tenant HNSW graphs (`m = 0`, `payload_m = 16`), and a full scan when the filtered set is below `full_scan_threshold` (10 MB of vectors, about 3,300 at 768 dimensions); tiered multitenancy promotes a tenant to its own shard at ~20k points. Weaviate gives each tenant its own shard; its dynamic index stays flat (exact) until 10k objects, and filtered queries go exact below `flatSearchCutoff` = 40k. Milvus's partition-key isolation builds an index per tenant; Pinecone and Turbopuffer use one namespace per tenant. Elastic advises exact search below ~10k documents after filtering; Lucene and OpenSearch fall back to exact scoring when the filter matches few documents or the approximate search returns fewer than k. Every product guarantees k results.

## Research findings and exact-search cost
Research agrees that post-filtering a shared index loses recall at low selectivity and that equality filters on a known attribute are best served by per-value (per-tenant) indexes. ACORN (SIGMOD 2024) shows post-filtered HNSW cost grows with 1/selectivity and fails to reach 0.9 recall when a query's neighbours mostly fall outside the filter; it pre-filters exactly below roughly 1–8% selectivity. A SIGMOD 2026 study running filtered methods inside pgvector (arXiv 2603.23710) found Postgres adds up to 10× overhead, iterative-scan throughput drops 89% under negative correlation at 1% selectivity, and pre-filtering won only at very low selectivity. The VLDB 2025 filtered-search tutorial names a partitioned index per attribute value as optimal when every query has such an equality filter. The BigANN 2023 filtered-track winner searched rare tags exhaustively and used graphs only for common ones. Exact-search cost is unmeasured for Connapse: a 768-dim vector is 3 KB (stored out of line in TOAST), and estimates put a single-core scan at a few ms per 10k vectors and 0.3–0.6 s per 1M, with Postgres overhead on top.

## Recommendation for Connapse
1. **Keep exact search for containers up to a measured threshold** (literature suggests 10k–50k vectors). Make it container-local: the planner already has B-tree indexes on `chunk_vectors.owner_id` and `model_id`; confirm plans start from the container at scale, not from all documents.
2. **Stop building one shared IVFFlat index per model.** It is unused today and becomes a recall hazard (probes = 1, post-filtering, untrained lists) the day the planner picks it.
3. **For large containers, add per-container ANN**: list partitioning of `chunk_vectors` by container with HNSW per large partition, or partial HNSW indexes for the few largest containers; always search with `hnsw.iterative_scan` and an explicit `ef_search`, and fall back to exact when fewer than 30 hits return. This works identically self-hosted and on Azure (pgvector 0.8.2).
4. **Leave pg_diskann and pgvectorscale aside** until in-index filtering reaches Azure flexible server.
5. **Measure before choosing thresholds**, with the test plan below.

## Test plan (extends the #570 `vector-index` probe)
Build tenants of 1k, 10k, 100k and 1M vectors from real embeddings (sampled distinct documents, not noised copies, which inflate recall; uniform random vectors understate ANN recall) in databases of 1M–10M rows; compute exact top-30 ground truth; compare the current plan, HNSW and IVFFlat with iterative scans across `ef_search` / probes / `max_scan_tuples`, and per-container indexes; report recall@10/@30, result completeness and p50/p95/p99 latency (warm and cold), recall variance across tenants, and exact-scan latency versus tenant size with and without `STORAGE PLAIN` and parallel workers.

## Conflicts and uncertainties
- Exact-search switch points differ by source: ~3.3k (Qdrant at 768 dims), 10k (Weaviate, Elastic), 40k (Weaviate filtered), ~50k (Neon), up to 10^5 (Faiss lore). None were measured on Connapse's query shape.
- AWS's pgvector 0.8 benchmark measures completeness, not recall; the SIGMOD 2026 paper shows iterative scan can collapse under negative correlation.
- Whether IVFFlat recall degrades on growing data is inferred from its training step, not quoted from the maintainer.

## Gaps — what we did not find
- A measured pgvector exact-scan latency curve for 768-dim vectors versus rows.
- Filtered-recall numbers for pg_diskann, pgvectorscale label filtering or HorizonDB.
- Whether HorizonDB-style in-index filtering will reach Azure flexible server.
