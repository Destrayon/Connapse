# Which two or three connectors should Connapse build next, judged on RAG shape, adoption, chunker-shape distinctness, GraphRAG readiness, and per-object permission parity?
**Date:** 2026-09-09
**Status:** Reviewed
**Built on:** highest-value-connectors-2026-08-13.md (demand catalog survey, legal blockers, credential friction, and the file-shaped versus record-shaped contract finding are carried forward, not re-derived)

## Executive summary

Build **GitHub** (repository code plus issues and pull requests) first, then an **Atlassian pair, Confluence Cloud and Jira Cloud** sharing one credential, one identity mapping, and one Atlassian Document Format renderer. GitHub is the only candidate that scores at the top on all five criteria: it is the number-one source among developers who wire MCP servers into coding agents, code is the content shape most unlike Connapse's five prose chunkers, GitHub exposes the richest typed edges (issue closes pull request, pull request touches file, cross-references) for a structure-first knowledge graph, and per-object permission parity is one live API call per repository. Confluence keeps the strongest general-market demand signal and has a per-page live permission check; Jira rides on the same credential for a small cost, has the best bulk permission check of any source surveyed, and its typed issue links are the bridge that connects Confluence pages to GitHub code in a graph. Notion is disqualified by the per-object rule because its API exposes no per-user access at all. SharePoint is cheap but brings no new shape, weak GraphRAG structure, and near-zero pull with the MCP audience.

The key uncertainty is the chunker hypothesis itself: the literature supports shape-specific chunking clearly for code, chat, and tables, but for wiki pages and tickets the measured gains come from adding context to chunks, not from new boundary rules. If testing the hypothesis is the priority, Slack is the sharpest experiment (a 10 to 18 point swing between turn-level and segment-level units in one ICLR 2025 study), but it is the weakest RAG corpus and the weakest adoption win, so it is listed as an optional third, not a recommendation.

## Research brief

**Question:** Which two or three connectors should Connapse build next to maximize adoption, exercise distinct content shapes for shape-specific chunkers, and set up GraphRAG, given that every connector must filter search results per object at parity with the source and fail closed?

**Sub-questions investigated:**
1. Content shape per candidate, and whether evidence exists that a shape-specific chunker beats generic prose chunking for that shape.
2. Native graph structure exposed by each source's API, and whether GraphRAG's benefit depends on source-native structure versus LLM entity extraction.
3. Whether each candidate can support per-object, per-user permission filtering at parity with the source, evaluated live at query time, failing closed.
4. Adoption demand refreshed since August 2026, with a new angle on the MCP and coding-agent audience, plus .NET engineering cost.

**Out of scope:** legal and terms-of-service analysis (done August 2026; Zendesk and Box remain excluded), email, CRM and ITSM sources, web crawl, embedding provider choice.

**Success criteria:** a ranked build order of two to three connectors with the reasoning per criterion, explicit disqualifications, and the conflicts and gaps that could change the answer.

## Findings by sub-question

### Sub-question 1: Content shape and evidence for shape-specific chunking

This section claims that shape-specific chunking is evidence-backed for source code, chat, and tables, and is NOT evidence-backed as a boundary strategy for wiki pages or tickets, where the gains come from context injection.

The strongest evidence that chunking matters at all is Chroma's 2024 evaluation (roughly nine points of recall between the best and worst chunker, with OpenAI's default configuration ranked last) and a 2026 study across 36 chunkers and six domains (structure-aware paragraph grouping reached nDCG@5 of 0.459 against under 0.244 for fixed-character splitting, and "no single chunking strategy is universally optimal"). The strongest counter-evidence is Vectara's NAACL 2025 paper, which found chunker differences of about one point on prose while swapping the embedding model moved F1 by 7.4 points. These reconcile: gains are small when comparing fixed versus semantic breakpoints on prose, and large when the baseline destroys structure (line-splitting code, linearizing tables).

Per shape:

- **Source code (GitHub, GitLab, local Git).** Meaning is carried by syntactic units and identifiers, not sentences; every existing Connapse chunker splits on punctuation code lacks. A tree-sitter-based chunker emitting AST-aligned units is the shape-specific design. The cAST paper (EMNLP 2025 Findings) reports +1.8 to +4.3 Recall@5 over fixed-size line chunking across three embedders and +2.6 Pass@1 on SWE-bench. A 2026 controlled study of 864 settings found AST chunking tied a plain sliding window and that one-chunk-per-function was 3.6 to 5.6 points worse, so the benefit is avoiding mid-function cuts and bad granularity, not syntax boundaries as such. Cursor, Sweep, and CocoIndex all chunk with tree-sitter (secondary sources, no published deltas). Confidence: high that code needs its own chunker; medium on the gain size.
- **Issues and pull requests (GitHub, Jira, Linear).** A small record plus an ordered comment thread, usually under one chunk in total. The shape-specific design is record assembly (fields as a header, comments appended or as child chunks carrying the parent title), not boundary detection. No paper ablates issue-as-document against comment windows. Atlassian's Rovo team attributes its 26 to 40 percent retrieval uplift on Jira-like data to embedding fine-tuning and hybrid field signals, not chunking. Confidence: low that a dedicated chunker helps; this is the weakest test of the hypothesis.
- **Wiki pages (Confluence, Notion).** Heading-hierarchical prose where a section's meaning depends on the page title and ancestor headings. Connapse's DocumentAware chunker already splits on headings, so what is new is prepending a breadcrumb (space, parent pages, heading path). Anthropic's Contextual Retrieval cut top-20 retrieval failures from 5.7 to 3.7 percent with context prepending alone and to 1.9 percent with contextual BM25 and reranking. Late chunking (Jina) reports +1.5 to +1.9 nDCG, but a 2025 paper found it "sacrifices relevance and completeness", a conflict. Confidence: medium; context injection is well evidenced, a new boundary strategy is not.
- **Office documents (SharePoint, OneDrive, Google Drive).** Nothing new in shape beyond what the existing Office parser handles, except tables. Structure-aware table chunking (rows as key-value blocks under repeated headers) lifted hybrid MRR from 0.358 to 0.595 on 39K legal records in one 2026 paper. This is the largest measured gain of any shape but rests on a single source, and it can be tested on Connapse's existing Office and Azure Blob content without building any new connector.
- **Chat threads (Slack, Teams, Discord).** Short ungrammatical turns with speaker and timestamp; a single message rarely stands alone. SeCom (ICLR 2025) measured segment-level 69.3 versus turn-level 58.0 versus session-level 51.2 GPT4Score on LOCOMO, so granularity is the whole game and both too-fine and too-coarse lose badly. Snyk abandoned rolling-window chunking of Slack and instead extracts question-answer pairs per thread with an LLM, which suggests raw threads retrieve poorly even when chunked well. Confidence: high that chat needs its own unit; medium on whether chat is a good corpus at all.

Ranking by distinctness from the existing prose chunkers: code, chat, tables, issues, wiki. Ranking by strength of evidence that a dedicated chunker helps: tables, chat, code, wiki, issues.

### Sub-question 2: Native graph structure and GraphRAG readiness

This section claims that GraphRAG's benefit depends on query type rather than on source-native structure, but that source-native structure makes the graph cheap and complete, and that GitHub and Jira expose the most useful typed edges.

GraphRAG-Bench (ICLR 2026) found vanilla RAG with reranking beat every GraphRAG variant on fact retrieval (60.9 percent versus 49.3 for Microsoft GraphRAG and 58.6 for LightRAG), while HippoRAG 2 led on complex reasoning (53.4 versus 42.9) and graph methods led on contextual summarization (about 64 versus 51.3). A systematic evaluation from MSU and Meta found the same split and measured that only 65.8 percent of answer entities appeared in LLM-extracted knowledge graphs, so extraction-built graphs are incomplete as well as expensive (full Microsoft GraphRAG indexing costs roughly a thousand times vector RAG; LazyGraphRAG exists to avoid that). Vendor win-rate tables should be treated as upper bounds: Microsoft's later work showed one method's 66.7 percent LLM-judged win rate fell to about 39 percent after position and length correction.

Systems that build the graph from author-defined links instead of extraction get it almost free and report gains: Wikipedia hyperlink path retrieval (+14 points on HotpotQA), LARAG following existing HTML links, GraphCoder (+6 exact match over RAG baselines), and KGCompass, which joins issues and pull requests to files, classes, and functions and found that 69.7 percent of bugs it localized needed multi-hop traversal. Atlassian's own Teamwork Graph and Glean's knowledge graph both lead with containment and reference edges (page contains, owns ticket, references project) before inferred ones.

### Sub-question 3: Per-object permission parity, live at query time, fail closed

This section claims that GitHub, Confluence Cloud, Jira Cloud, and SharePoint can meet the rule with live evaluation, Slack can at channel granularity, Confluence Data Center is unverified, and Notion cannot meet it at all.

- **GitHub (Cloud and Enterprise Server).** Identity: on Enterprise Cloud with SAML, the GraphQL externalIdentities query maps a SAML nameId to a GitHub login, readable with an org-owner token or a GitHub App with Members read. Check: `GET /repos/{owner}/{repo}/collaborators/{username}/permission` returns the highest effective role across repository, team, organization, and enterprise grants, and 404 means no access. One call per distinct repository in the hit set, not per file, within 5,000 requests per hour for a PAT or 15,000 for an Enterprise Cloud App. Native granularity is the repository, which fans out to every file under the per-object principle. Traps: internal repositories are readable by every enterprise member and public ones by everyone, so a 404-based check must be paired with visibility. Enterprise Server identity mapping is by login or email and unverified. Confidence: high.
- **Confluence Cloud.** Identity: Atlassian accountId; email lookup respects profile privacy, so a hidden email must fail closed (the organization admin API can return emails regardless). Check: `POST /wiki/rest/api/content/{id}/permission/check` with a user subject and the read operation evaluates site, space, and content restrictions including inherited view restrictions; checking another user requires Confluence Administrator. One call per hit under the points-based quota (a shared 65,000 points per hour pool by default), fine for tens of searches per hour with short caching. Traps: a Forge app calling as itself gets false for everything; edit-only restrictions do not hide content; anonymous space access. Confidence: high.
- **Confluence Data Center.** Only the "is this user explicitly named in the restriction" endpoint is confirmed; no permission-check endpoint was found in the Data Center reference, though the client-rendered docs could not be fully verified. A live check would mean reconstructing space permissions, ancestor restrictions, and group membership, which is fragile. Confidence: low. This reverses the August report's "Data Center is materially easier" for the permission dimension.
- **Jira Cloud.** Same identity as Confluence. `POST /rest/api/3/permissions/check` takes an accountId and up to 1,000 issues and returns the issue ids the user may browse, honoring project permissions and issue security levels. One call per search. Checking another user requires Administer Jira. Trap: null or empty entries are silently ignored, so an empty response must be read as deny. Confidence: high, with the 1,000-issue limit taken from an official-page snippet that would not fully load.
- **SharePoint and OneDrive.** Identity: the Entra object id Connapse already resolves. Graph's driveItem permissions listing is trap-heavy (organization and anonymous links grant everyone, unredeemed invites may be missing, "Everyone except external users" appears as an opaque claim). Better: SharePoint REST `getusereffectivepermissions` for a named user, or an on-behalf-of read with the user's own token where 403 or 404 means deny. Delta can flag permission-only changes but needs Sites.FullControl.All. Confidence: medium-high.
- **Slack.** Identity: users.lookupByEmail. The permission unit is current channel membership via conversations.members; there is no per-message ACL and new members see full history, so channel membership evaluated live IS parity with Slack. A bot token cannot see private channels it was not added to, so those must fail closed. Slack Connect shared channels are a trap. Internal customer-built apps are exempt from the 2025 rate cuts on conversations.history. Confidence: high. This resolves the August report's open "ACL-flattening problem".
- **Google Drive.** Live parity is achievable only by impersonating the user through domain-wide delegation and calling files.get per hit; permissions.list does not expand groups, and anyone or domain entries with discovery enabled are fail-open traps. External users cannot be impersonated and must be denied. Confidence: medium.
- **Notion.** The Page object has no sharing or permission fields, integrations only see pages shared with them, and the changelog shows no change through 2026. Disqualified under the per-object rule. Confidence: high.

### Sub-question 4: Adoption demand refresh and .NET engineering cost

This section claims that GitHub is the number-one source for Connapse's MCP and coding-agent audience, Confluence remains the number-one general-market signal though down 26 percent, and SharePoint and Google Drive barely register with the MCP audience.

Demand since June 2026: the three top-reacted Onyx connector requests cited in August (GitHub source-code indexing, Teams, GitLab code) are all now closed and shipped, so they signal table stakes rather than an open gap. RAGFlow shipped Outlook, OneDrive, Teams, Slack, SharePoint, Salesforce, and Azure Blob in one June release. Open WebUI's "data sources" request remains open at 51 reactions, the largest unmet connector demand in any self-hosted tool, with the community filling it via a sync tool covering Confluence, Notion, Jira, Slack, and git. LlamaIndex reader downloads over the last 30 days: Confluence 165,255 (down 26 percent from August), GitHub 64,344 (flat), Jira 32,485 (flat), Notion 31,496, OneDrive 5,466, SharePoint 4,266.

MCP-audience signal (new): by MCP search interest (Ahrefs via mcpmanager, March 2026, single source), GitHub 69k, Jira, Atlassian, and Confluence combined 40k, Notion 23k, Slack 17.7k, Linear 10.6k, Google Drive 5.9k at number 25, SharePoint absent from the top 50. Repository stars: github-mcp-server 32.8k, the community mcp-atlassian 5.9k (it supports Server and Data Center, a tell that self-hosters want Confluence), notion-mcp-server 4.6k, the best-known Google Drive MCP 283 stars and unmaintained. Claude Code's own MCP docs use GitHub, Notion, Slack, Sentry, and Microsoft 365 as examples; Atlassian's remote MCP went GA in February 2026. Those official servers are act-and-write tools with keyword search, and none offer cross-source semantic search, which is the gap Connapse fills for sources people already have wired in.

### Cross-criterion scoring and recommendation

This section claims that GitHub, then Confluence Cloud plus Jira Cloud, is the build order, with Slack as an optional third only if testing the chunker hypothesis outranks adoption.

| Source | RAG shape | Adoption pull | Chunker test | GraphRAG structure | Permission parity | Verdict |
|---|---|---|---|---|---|---|
| GitHub code plus issues and PRs | Strong (code, markdown, records) | Number one for MCP audience | Sharp (code) plus weak (issues) | High, typed, free | Live, per repo, high confidence | Build first |
| Confluence Cloud | Strong (wiki prose) | Number one general market | Medium (breadcrumb context, not boundaries) | Medium (hierarchy free, links DIY) | Live, per page, needs Confluence admin credential | Build second |
| Jira Cloud | Medium (short records) | Rides on Confluence | Weak | High, and the bridge to GitHub and Confluence | Live, bulk, best of all | Build with Confluence |
| Slack | Weak (raw threads retrieve poorly) | Moderate | Sharpest (chat granularity) | Medium | Live, per channel, fail closed on invisible private channels | Optional third for the hypothesis only |
| SharePoint and OneDrive | Same as existing Office files | Near zero with MCP audience | None new (tables testable today) | Low | Live, per item, medium-high | Skip for now |
| Notion | Strong | Moderate | Medium | Medium-high | None; API exposes no per-user access | Disqualified |
| Google Drive | Strong | Low with MCP audience | None new | Low | Live only via domain-wide delegation | Skip |

Two implementation notes fall out of the findings. First, the record-shaped sibling to the file-shaped connector interface, called out as the Tier 0 prerequisite in August, is still needed for issues, Jira, and Confluence pages; GitHub is the right pilot because repository files work through the existing interface today and only issues need the new one. Second, the table-chunking result, the largest measured gain in the chunking literature, can be tested against content Connapse already ingests, so it does not need to influence the connector choice.

## Conflicts and uncertainties

This section lists every disagreement between sources, and between this run and the August 2026 report, that could change the recommendation.

- **Magnitude of chunking gains.** Chroma 2024 and the 2026 36-chunker study call chunking a large lever; Vectara NAACL 2025 finds it small relative to embedding choice. Reconciled by baseline: the large gaps appear only when the baseline destroys structure.
- **AST chunking for code.** cAST (EMNLP 2025) reports it beats fixed-size splitting; a 2026 study of 864 settings finds it ties a sliding window. Both agree per-function chunks are worse.
- **Late chunking.** Jina reports +1.5 to +1.9 nDCG; a 2025 paper finds it loses relevance and completeness.
- **Confluence Data Center.** The August report called it materially easier (PATs, native webhooks, no points limits). Under the per-object rule it is harder, because no per-user permission check endpoint could be confirmed. Unresolved; verify against a live Data Center instance.
- **Atlassian credential.** The August report favored bring-your-own API token. This run finds that checking another user's permission requires Confluence Administrator or Administer Jira, so the connecting credential must belong to an admin. Compatible, but it raises the bar on who can set the connector up.
- **Slack.** The August report deferred Slack until the "ACL-flattening problem" had a designed answer. This run finds channel membership evaluated live is parity with Slack's own model, so the blocker is resolved; the remaining reason to defer is RAG quality, not permissions.
- **Notion.** The August report placed Notion in Tier 2. Under the hard constraint it is disqualified.
- **Onyx demand signals.** The August report's top-reacted requests are now shipped features, so they no longer indicate an open gap.
- **Confluence demand.** Reader downloads fell 26 percent in one month, from 224,808 to 165,255, while GitHub and Jira held flat. One data point; could be seasonal.
- **GraphRAG win rates.** LightRAG reports 60 to 85 percent LLM-judged wins over naive RAG; GraphRAG-Bench shows it losing on fact retrieval, and bias correction shrank one vendor win rate by about 25 points. Trade-press figures such as "86 versus 32 percent" are not supported by peer-reviewed benchmarks, which show 3 to 13 point gaps.

## Gaps, what we did not find

- No per-user permission check endpoint confirmed or denied for Confluence Data Center.
- No published ablation of issue-as-document versus comment-window chunking for tickets.
- No evaluation of breadcrumb-prepended wiki chunks with recall numbers; only a secondary write-up.
- No data on Connapse's own users; every demand signal remains a proxy.
- GitHub Enterprise Server identity mapping (SAML or LDAP to login) not verified from official docs.
- Notion.Net 6.0 appears in search results but not in the release feed.
- Two October 2025 repository-graph papers claiming large relevance gains were abstract-only and unverified.
- The Jira bulk permission check's 1,000-issue limit and admin requirement come from an official page that would not fully render.

## Source quality assessment

The chunking and GraphRAG findings rest mainly on primary sources: peer-reviewed papers (EMNLP, NAACL, ICLR, ICML, ASE) and vendor engineering posts with published numbers (Anthropic, Microsoft Research, Chroma, Jina). The permission findings rest on official API documentation for every candidate, with three community-sourced details flagged (the Confluence Relation API returning empty arrays, the "Everyone except external users" claim string, Graph omitting unredeemed invites). The demand refresh mixes primary registries and changelogs (Onyx, RAGFlow, GitHub API, pypistats, NuGet) with one secondary single-source ranking (Ahrefs search interest via mcpmanager). No recommendation depends on a tertiary source. The August 2026 report's demand findings were primary (catalog enumeration) and its market-share figures tertiary; only the primary parts were carried forward.
