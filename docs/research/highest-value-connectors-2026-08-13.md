# Which data-source connectors should Connapse build next?

**Date:** 2026-08-13
**Status:** Reviewed
**Built on:** no prior corpus material (Connapse MCP was not available in this session, so no corpus pre-check was possible)

## Executive summary

This report ranks candidate data-source connectors for Connapse, the self-hosted .NET 10 RAG platform, on demand, engineering feasibility, and legal risk. The headline finding is that the two candidates with the best pure engineering profile — **Zendesk and Box** — are the two you should not build, because both vendors' terms of service explicitly prohibit creating persistent indexes or caches of their API data, which is precisely what a RAG index is. The second finding is structural: Connapse's `IConnector` contract is file-shaped (path, size, lastModified, byte stream) and its cloud sync is a 5-minute full-list-and-diff poll, and both of those must change before the highest-value connectors can be built well — roughly half the high-demand sources are record-shaped, and nearly all of them offer a real delta cursor that the current polling model cannot exploit.

Recommended build order is **Git (local + GitHub/GitLab) → Microsoft Graph (SharePoint/OneDrive) → Confluence**, preceded by a contract change that adds cursor-based incremental sync. Confluence is the single strongest demand signal found (the only source present in all eight connector catalogs surveyed, and 3–7× GitHub's LlamaIndex reader download volume), but Git is the best value-per-engineering-day and matches Connapse's developer-facing identity. The largest uncertainty is that every demand signal in this report is a proxy — competitor catalogs, GitHub issue reactions, and package downloads — because no data on Connapse's own users was available.

## Research brief

**Question:** Which data-source connectors would deliver the highest value if built for Connapse next, given that Connapse must define the ingestion and sync process while the user supplies only credentials?

**Sub-questions investigated:**
1. How do the file-shaped cloud document stores (Google Drive, OneDrive/SharePoint, Box, Dropbox) compare on auth, incremental sync, rate limits, content extraction, and .NET SDK health?
2. How do record-shaped knowledge and collaboration sources (Notion, Confluence, Jira, Slack, Zendesk, Linear) compare on the same axes, plus document assembly cost, deletion detection, and ACL exposure?
3. How do developer and public-web sources (GitHub, GitLab, web crawl, RSS, local Git) compare, and which gives the best value per engineering day?
4. What does revealed preference across comparable products' connector catalogs and user feature requests say about actual demand?
5. How hard is it for a *self-hosted, often firewalled* deployment to obtain working credentials for each provider — including OAuth redirect-URI constraints, app-verification burden, and webhook reachability?
6. (Added mid-investigation) Are email sources — Gmail, Outlook/Graph, IMAP — worth building at all?

**Out of scope:** implementation design for any specific connector; pricing or business-model questions; changes to Connapse's chunking, embedding, or search layers; non-document data sources such as SQL databases or data warehouses.

**Success criteria:** a ranked, decision-ready build order with explicit reasoning, and explicit identification of any candidate that should be rejected.

## Findings by sub-question

### The architectural constraint: Connapse's connector contract is the real bottleneck

Before any ranking of external data sources matters, two properties of Connapse's own connector layer bound what is achievable. First, `IConnector` (in `src/Connapse.Core/Interfaces/IConnector.cs`) is **file-shaped**: it models a source as `ListFilesAsync` returning `(Path, SizeBytes, LastModified, ContentType)` tuples plus `ReadFileAsync(path)` returning a `Stream`. Google Drive, OneDrive/SharePoint, Box, Dropbox, and Git repositories map onto this cleanly. Notion pages, Confluence pages, Jira issues, Slack threads, and Zendesk tickets do not — they are records assembled from multiple API calls, with no byte stream and no natural path. Adapting them behind the file interface requires a synthetic path scheme and discards structure the source provides for free. A sibling record-shaped interface is the better answer than an adapter.

Second, Connapse's cloud connectors currently poll every five minutes, list the entire remote corpus, and diff it against an in-memory snapshot. That is O(entire corpus) per poll and it discards the single most valuable capability nearly every source in this report offers: a durable cursor or delta token. Microsoft Graph's `/delta` charges 1 resource unit for a delta-token call versus 2 for listing children, and returns deletions explicitly. Google Drive's `changes.list` with a page token never re-lists. Dropbox's `list_folder/continue` cursor and Zendesk's incremental export cursors work the same way. Git's `diff --name-status` between two commit SHAs is an exact changed-file list including deletions, for free. **Adding an optional cursor capability to the connector contract is a prerequisite, not a follow-up** — without it, every connector built from here is throttled to the weakest sync mode available.

### Sub-question 1: File-shaped cloud document stores (Drive, SharePoint/OneDrive, Box, Dropbox)

**Microsoft Graph (OneDrive/SharePoint) has the best incremental sync of any source surveyed.** `/drives/{id}/root/delta` returns paged results ending in a durable `@odata.deltaLink`; `?token=latest` skips initial enumeration entirely; and `HTTP 410 Gone` with `resyncChangesApplyDifferences` is an explicit, documented resync contract ([Graph delta docs](https://learn.microsoft.com/en-us/graph/api/driveitem-delta)). Office files download as native OOXML with no export step. Rate limits are resource-unit based at 1,250–6,250 RU/min per app per tenant, scaling with tenant license count ([SharePoint throttling](https://learn.microsoft.com/en-us/sharepoint/dev/general-development/how-to-avoid-getting-throttled-or-blocked-in-sharepoint-online)) — the tightest ceiling of the four on small tenants, and Microsoft does block persistently non-compliant apps, so honoring `Retry-After` and decorating `User-Agent` as `NONISV|Company|App/Version` is mandatory. `Microsoft.Graph` 6.5.0 (2026-08-06) targets net10.0. Two gotchas: SharePoint requires a `site → drive → driveItem` discovery step, and delta responses omit `path` from `parentReference` while folder renames do not re-emit descendants, so Connapse must key on item ID and maintain its own path index.

**Google Drive's sync is good and its auth is less painful than it first appears.** `changes.getStartPageToken` → `changes.list(pageToken)` is pure token polling with no re-listing ([manage changes](https://developers.google.com/workspace/drive/api/guides/manage-changes)). Quotas are generous (325,000 units/min/user; `files.list` costs 100 units, a download 200) though the 1 TB/day/project egress cap bounds bulk ingest ([limits](https://developers.google.com/workspace/drive/api/guides/limits)). Native Google Docs require `files.export`, which does support `text/markdown` for Docs but imposes a **hard 10 MB cap on exported content** ([files.export](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/export)). The structural fit is the worst of the four: files are identified by ID not path, duplicate filenames within a folder are legal, and shortcuts complicate the hierarchy — although Shared Drive files must have exactly one parent, so scoping a container to a Shared Drive makes the model tree-shaped again ([shared drives](https://developers.google.com/workspace/drive/api/guides/about-shareddrives)).

**Box and Dropbox are technically strong.** Box is the best structural match of all four — a genuine tree with stable paths and duplicate names blocked within a folder — with a `stream_position` cursor and long polling that works from behind NAT, and a generous published limit of 1,000 requests/min/user ([Box rate limits](https://developer.box.com/guides/api-calls/permissions-and-errors/rate-limits/)). Dropbox has the lowest auth ceremony and its `/files/list_folder/longpoll` blocks until a change **with no public endpoint required** ([detecting changes](https://developers.dropbox.com/detecting-changes-guide)), which is close to ideal for firewalled self-hosting. Both, however, are subject to the legal finding in sub-question 5 (Box) or weak demand (Dropbox), covered below. Dropbox also does not publish exact rate limits, making capacity planning guesswork, and `Dropbox.Api` 7.2.0 is netstandard2.0-only and still on Newtonsoft.Json.

### Sub-question 2: Record-shaped knowledge and collaboration sources

**Notion's economics changed in February 2026 and the standard objection to it is now obsolete.** `GET /v1/pages/{id}/markdown` returns a full page as markdown in a single call ([Notion changelog](https://developers.notion.com/page/changelog)), eliminating the recursive `GET /v1/blocks/{id}/children` walk that historically cost 5–30 calls per page. Budget roughly 2 calls per page. What remains difficult: the ~3 req/s rate limit makes a large workspace a multi-hour backfill, deletions are **silently invisible** (archived pages simply drop out of search results, forcing periodic full re-list reconciliation), there is no ACL API at all, and every page must be individually shared with the integration — there is no "index my workspace" operation. Note also that API version `2025-09-03` split databases into "data sources" and moved the query endpoint ([upgrade guide](https://developers.notion.com/docs/upgrade-guide-2025-09-03)).

**Confluence is the strongest demand signal but has the weakest deletion story.** Bodies are not returned by default — you must request `body-format=storage` (XHTML-ish) or `atlas_doc_format` (ADF JSON), and neither is plain text, so **Connapse must implement a renderer**. Rendered HTML via `body-format=view` exists only on get-by-id, not on list endpoints ([CONFCLOUD-79781](https://jira.atlassian.com/browse/CONFCLOUD-79781)). Incremental sync via CQL `lastmodified` or v2 `sort=-modified-date` works for updates, but trashed pages vanish silently and the webhooks that would report them (`page_removed`, `page_trashed`) **require a Connect or Forge app descriptor**, not plain OAuth or an API token ([webhook module](https://developer.atlassian.com/cloud/confluence/modules/webhook/)). Confluence **Data Center** is materially easier: Personal Access Tokens, native webhooks, no points-based rate limits, and v1 `expand=body.storage`. Confluence Cloud's ACL exposure is the best of any source surveyed — content restrictions and space permissions are both queryable, making genuine per-user filtering feasible.

A notable and load-bearing finding: Atlassian's new points-based rate limiting, enforced from 2026-03-02, states that **"API token-based traffic is not affected by this change"** ([Atlassian rate limiting](https://developer.atlassian.com/cloud/confluence/rate-limiting/)). If accurate, BYO-API-token auth is simultaneously the simplest credential *and* the higher-throughput path, making OAuth strictly worse for this connector — but see the conflict register, because Atlassian's acceptable-use guidance points the other way.

**Jira is solid and shares a credential with Confluence.** The same email + scoped API token works for both. Incremental sync via JQL `updated >= "-5m" ORDER BY updated ASC` is clean, and unlike Confluence, `jira:issue_deleted` webhooks are registrable via plain REST with no Connect descriptor. One breaking change has already landed: `/rest/api/3/search` is sunset and returns 410 Gone; the replacement `POST /rest/api/3/search/jql` requires an explicit `fields` list and uses `nextPageToken` with no `total`. Descriptions are ADF JSON on api/3, so the same renderer Confluence needs is reusable.

**Linear is the cheapest connector in this entire report, and Slack is the most expensive.** Linear returns issue, description, comments, labels, and project in a single GraphQL query with descriptions already in markdown — the lowest assembly cost of any source — and `trashed`/`archivedAt` are queryable so deletions are detectable by polling. Its limitation is market size, not engineering. Slack sits at the opposite extreme: assembling a busy channel's history requires `conversations.list` → paged `conversations.history` → `conversations.replies` per threaded parent, roughly 850+ calls for a 5,000-message channel, and there is no natural document unit (a thread is the least-bad choice). Slack's saving grace for self-hosted specifically is covered in sub-question 5.

**Zendesk has, on pure engineering merit, the best incremental sync of any source in this report** — purpose-built Incremental Exports (`/api/v2/incremental/tickets/cursor?start_time=`), 1,000 records per page, help-center article bodies delivered as ready-to-use HTML with zero assembly cost, `user_segment_id` exposed for ACL filtering, and **deletions genuinely surfaced** (deleted tickets remain in the export with `status: deleted` for ~120 days) ([incremental exports](https://developer.zendesk.com/documentation/api-basics/working-with-data/using-the-incremental-export-api/)). It is also the simplest credential of all: one API token in HTTP Basic. It should nonetheless not be built — see sub-question 5.

### Sub-question 3: Developer and public-web sources

**Git is the best value-per-engineering-day of any candidate.** For a local or cloned repository, `git pull` followed by `git diff --name-status <oldSha> <newSha>` yields an exact changed-file list *including deletions and renames*, with no rate limit, no pagination, no truncation cap, and no cursor-expiry edge cases. Every SaaS incremental API in this report is an approximation of what Git gives away. Estimated cost is 2–3 days, and `LibGit2Sharp` 0.32.0 (2026-07-24) ships working native binaries, with shelling out to the `git` binary as a zero-interop-risk fallback.

**GitHub is the highest-demand developer source and polls almost for free.** Authenticated conditional requests returning `304` **do not count against the primary rate limit** ([REST best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)), so frequent polling is nearly costless — which matters enormously for a firewalled deployment that cannot receive webhooks. `GET /git/trees/{sha}?recursive=1` returns the whole tree with path, SHA, and size in one call (up to 100,000 entries / 7 MB before truncation), and diffing two trees by blob SHA gives exact adds and deletes. Prefer that over the Compare endpoint, which **caps at 300 files**. Auth is a fine-grained PAT paste, with the caveat that org owners can require approval and an unapproved token silently degrades to public-data-only. Rate limits are 5,000/hr authenticated; the trap is the search API at 30/min and code search at only 10/min ([rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)). Markdown and code need no parser at all. Note `Octokit` 14.0.0 has not shipped a release in ~19 months — maintained but slow, so newer endpoints may need hand-rolling.

**GitLab is the same shape for the same effort with a healthier SDK but a smaller user base.** `NGitLab` 12.0.0 (2026-07-31) explicitly targets net10.0. GitLab.com allows 2,000 authenticated req/min per user, far more generous per-hour than GitHub. The weakness is that ETag/304 conditional-request support on the REST API appears unimplemented ([gitlab-foss#26926](https://gitlab.com/gitlab-org/gitlab-foss/-/work_items/26926) is still open), so free polling does not carry over.

**Web crawl has the highest ceiling and the worst effort-to-reliability ratio.** No credential at all is required, which is a real advantage, but HTML→text extraction quality, robots.txt compliance (RFC 9309 requires assuming complete disallow on a 5xx), canonicalization, and deduplication form a long bug tail. The mature .NET stack exists — AngleSharp 1.7.1, SmartReader 0.11.1, ReverseMarkdown 6.2.1, all actively maintained as of August 2026. The cost cliff is JavaScript-rendered sites: `Microsoft.Playwright` 1.62.0 is a **201 MB package** with bundled browsers, which would roughly double a slim Connapse container image. Ship static-HTML-only in v1. RSS/Atom is the cheapest connector on the list at 1–2 days using the Microsoft-maintained `System.ServiceModel.Syndication`, but feed content is usually a truncated summary, so full text drags in the entire web-extraction stack anyway.

Microsoft 365 versus Google Workspace depends entirely on the unit of measure — ~446M paid M365 seats versus Google Workspace leading on *domain count* — and these two framings disagree because they measure different things, neither from a filing.

### Sub-question 5: Self-hosted credential friction, and the legal blockers

This sub-question produced the report's most consequential findings, because it inverts several rankings that pure engineering merit would suggest.

**Two candidates are contractually blocked.** Zendesk's Developer Terms §3.6 bans creating "persistent copies, archives, indexes, or long-term data stores using API Data," bulk export, and use for "creating, training, or improving any general AI model" ([Zendesk Developer Terms](https://www.zendesk.com/company/agreements-and-terms/zendesk-developer-terms/)). Box's Terms of Service §10 prohibits "periodic caching of information stored by Box" and §25.2 bars anyone who would "mine or analyze any Content" ([Box ToS](https://www.box.com/legal/termsofservice)). Both clauses read directly onto what a RAG indexer does. Zendesk is otherwise the best-engineered candidate in this report and Box the best structural fit — which makes this finding easy to miss and expensive to miss.

**Google's restricted-scope problem has a clean escape hatch for self-hosted specifically.** `drive`, `drive.readonly`, and `drive.metadata.readonly` are all **Restricted** scopes, and a centrally-hosted app using them would trigger annual CASA assessment at roughly $540–$1,500/yr. But if the *customer* registers the OAuth app in their own project with the consent screen set to **Internal**, no verification is required at any scope with no user cap ([Google: when verification is not required](https://support.google.com/cloud/answer/13464323)). Better still, a service account with domain-wide delegation needs no redirect URI at all. Because Connapse is self-hosted and every customer brings their own credentials, Connapse never incurs the CASA burden — it is pushed to the customer as consent-screen setup. This materially downgrades Google Drive's auth friction from High to Medium.

**Microsoft has the cleanest big-vendor story.** `http://localhost` and `http://127.0.0.1` are explicitly valid redirect URIs, arbitrary customer HTTPS hostnames are permitted (up to 256 per app), and client-credentials flow skips redirects entirely ([reply URL docs](https://learn.microsoft.com/en-us/entra/identity-platform/reply-url)). `Files.Read.All`/`Sites.Read.All` require tenant admin consent, but a customer registering their own app already has an admin in the loop. There is no vendor review process and no certification requirement for what Connapse would do.

**Slack is viable only because Connapse is self-hosted, and only in one specific configuration.** Since 2025-05-29 non-Marketplace apps get `conversations.history` and `conversations.replies` at **1 request/minute with a maximum of 15 objects**, but "internal customer-built apps will maintain their existing rate limits" of 50+ req/min and 1,000 objects ([Slack changelog](https://docs.slack.dev/changelog/2025/05/29/rate-limit-changes-for-non-marketplace-apps/)). Enforcement reached existing installs of unlisted distributed apps on 2026-03-03 and is now in force. A hosted or centrally-distributed Slack connector would be dead on arrival; a customer-registered internal app is fully functional. Slack's ToS separately prohibits persistent indexes of "**other organizations'** API Data" — the qualifier is the escape hatch, and it only holds if the customer creates the app in their own workspace and the data never leaves their org. Slack is also the only provider offering a first-class outbound-only push mechanism, **Socket Mode**, a WebSocket the app dials out over, which requires no public endpoint and surfaces `message_deleted` events in real time. The catch: Socket Mode apps are barred from the Slack Marketplace, so you cannot have both listing and outbound-only operation.

**Atlassian is technically easy and contractually ambiguous.** Atlassian's guidance explicitly names "asking customers to create individual apps for each Atlassian tenant" as an acceptable-use violation ([Atlassian guidance](https://www.atlassian.com/blog/development/building-secure-and-scalable-integrations-our-guidance-for-third-party-apps)), and 3LO apps allow exactly **one** callback URL, which is fatal for per-customer hostnames. The sanctioned firewall-friendly path is OAuth 2.0 client credentials for service accounts (no redirect URI, 5 free per org). API tokens still work but now carry a mandatory 365-day maximum expiry, so a pasted credential will eventually die and needs renewal-reminder UX.

**Salesforce should be dropped outright.** Spring '26 blocks new connected-app creation via both the UI and the Metadata API, re-enabled only by filing a Support case, making customer setup a ticketed project. AppExchange security review costs $999 per attempt with periodic re-review at the same fee. Combined with near-zero demand signal in the open-source cohort, it fails on every axis. (The Spring '26 lockdown is corroborated by multiple secondary sources but could not be primary-verified — help.salesforce.com is a JavaScript SPA that blocked direct fetching.)

**Ranked for outbound-only operation behind a firewall:** Slack (Socket Mode) > Salesforce (Pub/Sub gRPC) > GitHub (free conditional polling) > Dropbox (longpoll) > Box (`/events` long-poll) > Google / Microsoft / Atlassian / Zendesk (interval polling) > Notion (naive polling, worst).

### Sub-question 6: Email

**Do not build a general email connector.** Email is the highest-liability, lowest-signal corpus available. A typical corporate inbox is automated notifications, calendar invites, newsletters, and threads where each reply repeats the previous three verbatim under `>` quoting plus a signature and legal disclaimer. Naive ingestion produces an index where the same paragraph appears eight times and retrieval returns the *last* reply — the one with the least context. Fixing it requires quoted-text stripping (heuristics only, no reliable standard), signature detection, and thread-level rather than message-level chunking. That is a research project, not a connector. MIME parsing itself is solved — MailKit/MimeKit 4.17.0 is best-in-class and net10.0 compatible — but everything after it is not.

The governance problem is structural rather than legal: one shared vector index over N mailboxes means any search can leak any mailbox. Connapse's per-container isolation is the right primitive, but applying it correctly forces one container per user, which defeats cross-corpus search — the point of the product. Google's Workspace policy separately prohibits using data to "create, train, or improve a machine learning or artificial intelligence model beyond that specific user's personalized model" ([Workspace user data policy](https://developers.google.com/workspace/workspace-api-user-data-developer-policy)); a per-user index is arguably within the carve-out, a shared org-wide index over personal mailboxes is not.

If email is built anyway, build **Microsoft Graph first** — `/delta` returns deletions explicitly as `@removed: {reason: deleted}`, per-mailbox scoping is achievable via RBAC for Applications, and there is no vendor review. Gmail is worse on both counts: `gmail.readonly` is a **Restricted** scope (same tier as Drive), and `history.list` retention is "typically at least one week," after which an expired `startHistoryId` returns 404 and forces a full resync ([Gmail sync guide](https://developers.google.com/workspace/gmail/api/guides/sync)). One genuinely useful narrow scope: a **single designated shared mailbox** (support@, sales@) rather than personal inboxes — that is the case where email really is a knowledge base and the privacy problem evaporates.

### Recommended build order

**Tier 0 — prerequisite.** Extend the connector contract with an optional cursor/delta capability, and add a record-shaped sibling interface alongside the file-shaped `IConnector`. Every recommendation below is degraded without this.

**Tier 1 — build next.**
1. **Git family (local clone + GitHub + GitLab remotes).** Best value-per-engineering-day in the report (~2–3 days local, ~4–6 for GitHub), exact free incremental diffs including deletions, markdown and code need no parser, PAT-paste auth with no OAuth flow, no legal risk, and it matches Connapse's developer-facing identity (MCP server, CLI). Demand corroborates: 6/8 catalogs, Onyx's highest-voted request overall, and self-hosted Git variants outpolling SaaS sources on AnythingLLM.
2. **Microsoft Graph (SharePoint/OneDrive).** The strategic enterprise connector: best-in-class `/delta` sync, native Office files with no export step, Low–Medium self-hosted auth friction with no vendor review, excellent net10.0 SDK, 6/8 catalogs, and the largest enterprise seat base.
3. **Confluence (Cloud + Data Center).** The single strongest demand signal found — unanimous across catalogs and 3× GitHub's reader downloads. Ship the Data Center path too; it is materially easier (PATs, native webhooks, no points limits). Budget for an ADF/storage-format renderer, which Jira then reuses.

**Tier 2 — strong follow-ons.** Google Drive (7/8 catalogs, token-based sync, verification burden avoided via the Internal-app path; costs an export step and an ID-not-path model). Notion (the February 2026 markdown endpoint made it cheap; accept full-re-list deletion reconciliation). Web crawl, static-HTML-only (6/8 catalogs, zero auth, but the highest overrun risk — ship without headless rendering).

**Tier 3 — conditional.** Jira, once the Confluence renderer exists and shares its credential. Slack, only as a customer-registered internal app with Socket Mode, and only after the ACL-flattening problem has a designed answer. Linear, which is technically the cheapest connector in the report and makes an excellent low-risk pilot for the new record-shaped interface, though its market is small.

**Do not build.** Zendesk and Box (ToS prohibits persistent indexing, notwithstanding excellent engineering profiles). Salesforce (connected-app lockdown, $999 review, near-zero open-source demand). General email (bad RAG content, worst liability) — with a possible narrow exception for a Graph shared-mailbox connector.

## Conflicts and uncertainties

**Zendesk and Box: engineering merit versus contract terms.** The record-shaped investigation ranked Zendesk a top-two "first mover" on grounds of trivial credentials, grade-A incremental sync, and real deletion detection, and ranked Box the best structural fit among cloud drives. The credential-and-legal investigation independently found that both vendors' terms explicitly prohibit persistent indexes or caches of their API data. These findings are not factually contradictory — both are correct in their own domain — but they produce opposite recommendations, and this report resolves toward not building either. This resolution is a judgment call on unreviewed contract language and should be confirmed by counsel rather than taken from this document.

**Atlassian: is BYO-API-token the right path or an AUP violation?** Atlassian's rate-limiting documentation states that API-token traffic is exempt from the new points-based model, which argues for BYO tokens as both the simplest and fastest path. Atlassian's third-party integration guidance names "asking customers to create individual apps for each Atlassian tenant" as an acceptable-use violation. These likely do not literally conflict — an API token is not an app — but they point in opposite directions on how a self-hosted product should authenticate, and the safe reading (OAuth 2.0 client credentials for service accounts) forfeits the rate-limit exemption. Unresolved; verify with Atlassian directly before committing to a Confluence auth design.

**Google Drive auth friction: High or Medium?** The cloud-drive investigation rated it High on the basis of restricted scopes plus CASA. The credential investigation found the customer-registered "Internal" consent-screen path avoids verification entirely. Resolved toward Medium for Connapse's self-hosted BYO-credential model, but note the burden is *transferred* to the customer rather than eliminated, and that shows up as setup friction in onboarding.

**Load-bearing single-source claims.** Three findings materially shape recommendations and rest on one primary source each: Notion's `GET /v1/pages/{id}/markdown` endpoint (Notion changelog, Feb 2026) — this single fact moves Notion from expensive to cheap; Atlassian's API-token exemption from points-based limits; and Slack's internal-app rate-limit exemption (this last one has two corroborating Slack changelog entries, so it is the best-supported of the three). Verify the Notion endpoint against a live workspace before planning around it.

**Salesforce Spring '26 connected-app lockdown** is corroborated only by secondary sources; help.salesforce.com could not be fetched directly. The recommendation to drop Salesforce does not depend on this fact alone, so the uncertainty is not decision-relevant.

**Market-share figures conflict by construction.** Microsoft 365 versus Google Workspace reverses depending on whether you count paid seats or domains, and all figures in this report come from technographic inference sites or vendor blogs, not filings. They are directional context only and no recommendation rests on them.

## Gaps — what we did not find

- **No data on Connapse's own users.** Every demand signal here is a proxy: competitor catalogs, GitHub reaction counts on other products, and package download statistics. A single afternoon of asking actual Connapse users which source they would connect first would outweigh this entire sub-question. This is the largest gap in the report.
- **No vendor has published a "most requested connector" statement.** Searched across Onyx, Dify, RAGFlow, AnythingLLM, Glean, and Ragie blogs, roadmaps, and changelogs; none found. Absence of evidence, not evidence of absence — several changelogs are paginated and were not exhausted.
- **Glean's catalog was only verified through entries A–G** (the page paginates); later entries were inferred from vendor marketing copy and are marked as such.
- **Airbyte and Fivetran publish no most-used-source rankings**, and Zapier's "most popular apps" page returned 404, so the general-ELT popularity proxy could not be obtained.
- **Dropbox does not publish exact rate limits**, making capacity planning for that connector guesswork.
- **Box's text-representation API was not verified**, so the assumption that Box files must be downloaded and parsed locally may be pessimistic.
- **Implementation cost estimates exist only for the developer-source connectors** (sub-question 3). The SaaS connectors were not estimated in engineering days, so the value-per-day comparison across all candidates is partly qualitative.
- **No investigation of non-document sources** — SQL databases, data warehouses, S3-compatible object stores beyond what Connapse already supports — which were out of scope but may contain higher-value targets.

## Source quality assessment

The technical findings — API capabilities, auth models, rate limits, SDK versions — rest almost entirely on **primary sources**: official developer documentation, changelogs, NuGet package pages, and RFCs, all fetched live on 2026-08-13 and cited inline. Confidence there is high, with individually-marked exceptions.

The legal findings (Zendesk §3.6, Box §10/§25.2, Slack API ToS, Google Workspace user data policy, Atlassian AUP guidance) are **primary** in the sense that vendor terms pages were read directly, but they are **unreviewed by counsel** and involve applying general contract language to a specific product behavior. Treat them as flags requiring legal review, not as settled conclusions.

The demand findings are mixed. Connector catalog enumeration is **primary** (vendor pages and GitHub repositories read directly) and is the strongest part of the demand analysis. GitHub issue reaction counts are **primary** but small in absolute magnitude. LlamaIndex download statistics are **primary** (pypistats.org) but cover only four of the candidate sources due to rate limiting. Market-share figures are uniformly **tertiary** — technographic-inference vendors and SEO aggregator sites with undisclosed methodology, none traceable to a filing — and are flagged as such wherever used. No recommendation in this report depends on a tertiary source.
