# How should Connapse expose tables and nested data to agents through GraphQL?
**Date:** 2026-11-12
**Status:** Reviewed
**Built on:** nested-structured-tables-2026-11-11.md, rls-raw-sql-agents-2026-11-10.md,
con-304-table-permission-trimming-2026-11-10.md, con-328-table-head-to-head-2026-11-12.md

## Executive summary
CON-336 asks whether GraphQL gives agents one consistent way to query every kind of structured data in a
container, as a third option beside the structured table tools and agent-written SQL (`table_sql`). No published
study compares agents writing GraphQL with agents writing SQL on the same data, so the CON-336 runs will be the first
evidence we have. Every GraphQL layer that generates a schema from SQL tables (Hasura, PostGraphile, pg_graphql,
Directus, Data API builder, AppSync, StepZen, Grafbase) offers filters, ordering, paging, relationships and basic
aggregates. None of them can compute a median, a rank within a group, or arithmetic across columns, and only Directus
can bucket by month. We will build the GraphQL view ourselves. It parses queries with a small MIT parser and
validates them against a schema built for each caller. It runs every table read through Connapse's existing
structured-query service, so it inherits access trimming, row-level security and limits instead of copying them. The
main uncertainty is how well a frontier model writes GraphQL with two or more levels of nesting. The only accuracy
study (IBM, EMNLP 2024) tested small models, and two-hop queries were their weakest kind.

## Research brief
**Question:** What existing ways are there to expose tables and JSON/NoSQL-style data to LLM agents through GraphQL
(libraries, auto-generated schemas, safety limits)? Which parts can Connapse reuse to build a per-caller,
container-scoped GraphQL query tool?

**Sub-questions:**
1. What do auto-generated GraphQL schemas over SQL tables expose? This covers filters, relations, aggregates, group
   by, date bucketing, cross-column math and jsonb.
2. Which .NET libraries could serve the schema, given that tables are created at load time and differ per caller?
3. Which safety limits and per-tenant or per-user scoping patterns exist, and where have real systems leaked?
4. What is known about LLM agents querying through GraphQL, compared with SQL and with fixed tools?

**Out of scope:** GraphQL mutations or subscriptions, serving GraphQL over HTTP to people, and federation.

**Success criteria:** a decision on what to build versus reuse, the query shape agents get, and the safety limits
and leak tests the tool must have.

## Findings by sub-question

### 1. What generated GraphQL schemas over SQL tables expose
Generated GraphQL schemas share one shape: a list field per table with a filter object, ordering and paging; foreign
keys become nested relation fields; some tools add aggregates. Hasura v2 generates `<t>`, `<t>_by_pk` and
`<t>_aggregate`, with filters written `where: {col: {_eq: ...}}`, and the logical operators `_and`, `_or` and `_not`.
It has no group by: its docs send users to views or SQL functions, and the feature request is still open. Its jsonb
columns take `_contains`, `_has_key` and jsonpath operators ([Hasura query API][hasura-q],
[aggregates][hasura-agg], [group-by discussion][hasura-gb]). PostGraphile with `@graphile/pg-aggregates` adds
`groupedAggregates(groupBy, having)`, but it buckets dates only by hour and day ([pg-aggregates][pga],
[connection filter][pgf]). pg_graphql exposes `<table>Collection` connections, with aggregates turned off by default
and no group by. Its own docs say JSON "does not currently support filtering" ([pg_graphql API][pgg]). Directus is
the only tool whose GraphQL API documents month bucketing, as `groupBy: ["month(date)"]`
([Directus query parameters][directus]). Data API builder supports group by, but not on PostgreSQL
([DAB aggregation][dab-agg]). AppSync, StepZen and Grafbase generate neither aggregates nor group by
([AppSync introspection][appsync], [StepZen @dbquery][stepzen], [Grafbase Postgres][grafbase]).

**Not generated by any of the nine tools:** median or percentiles, ranks or other window functions, and arithmetic
across columns. Each tool points to a SQL view or function, which then appears as a new table or computed field
(confidence high: every tool's own docs agree). This confirms the CON-335 note's findings on pg_graphql and Hasura
(nested-structured-tables-2026-11-11.md).

**What we reuse:**
- Hasura's names and filter operators (`where`, `_eq`, `_gt`, `_in`, `_is_null`, `_and`/`_or`/`_not`, `order_by`,
  `<t>_aggregate`), because they are the most widely copied and the likeliest to be in a model's training data.
- PostGraphile's and Directus's `group_by` and `having` on aggregates.
- Nested fields from parent to child table: pg_graphql and Hasura generate them from foreign keys. For our child
  tables, the CON-335 link from `_parent_row` to `_row` stands in for the foreign key.

### 2. .NET libraries for a schema that differs per caller
Hot Chocolate 16.7 (MIT) can build types at runtime through `ITypeModule`. It has one schema per executor, though,
and no per-request or per-tenant schema. A schema per caller would mean building and caching our own executors. Its
filtering, sorting and projection features run over `IQueryable<T>` of entity classes, which our generated `t_<hex>`
tables don't have ([dynamic schemas][hc-dyn], [projections][hc-proj]). Data API builder runs as a separate service
from a static config file and can't aggregate on PostgreSQL ([DAB MCP][dab-mcp], [DAB aggregation][dab-agg]).
GraphQL.NET 8.8 builds code-first types as plain objects, but it would still need our resolvers ([GraphQL.NET][gqlnet]).
Two parser-only packages are available: GraphQL-Parser 9.5.1 (MIT, no dependencies, with a lexer, parser and AST
visitor, but no validation) ([GraphQL-Parser][gqlparser]), and HotChocolate.Language 16.7.5 (MIT) ([HC.Language][hclang]).

**Decision:** parse with GraphQL-Parser, then validate each query against a schema built from the tables and columns
the caller can read. Every table read and aggregate goes through the existing `ITableQueryService`. With a full
engine, every resolver would still have to call our compiler. We would also pay for per-caller schema builds and
write the executor cache ourselves. Meanwhile, access trimming, merged-table row filtering, hidden columns, row-level
security and the runner's limits stay where they are already enforced and tested.

### 3. Safety limits and scoping
GraphQL does not limit depth or the number of returned items by default. OWASP recommends limits on depth, list
size, cost and time, plus GraphQL-aware rate limits and turning off introspection and "did you mean" suggestions
([OWASP][owasp]). Published defaults:
- GraphQL Armor caps aliases at 15, depth at 6, directives at 50 and tokens at 1,000 ([Armor][armor]).
- GitHub requires `first`/`last` between 1 and 100 on every connection, caps a call at 500,000 nodes, and allows
  10 seconds per call ([GitHub limits][gh]).
- Shopify caps a query's cost at 1,000 points ([Shopify][shopify]).
- The IBM cost spec gives the static-cost model ([cost spec][costspec]).

Escape found unrestricted resource consumption in about 69% of 160 public GraphQL services ([Escape 2024][escape]).

**Two ways systems scope who sees what:**
- **A schema for each role.** Hasura, pg_graphql and PostGraphile build a schema per role, so a hidden field fails
  exactly as a field that doesn't exist ([Hasura roles][hasura-roles], [pg_graphql security][pgg-sec],
  [PostGraphile security][pgl-sec]).
- **One schema with runtime checks.** Data API builder rejects a query that names an excluded field, which tells the
  caller the field exists ([DAB authorization][dab-auth]), the same finding as
  con-304-table-permission-trimming-2026-11-10.md.

**Every confirmed leak came through a side path that skipped the main read path's check:**
- Hasura CVE-2026-54698: a `where` over a computed field ignored row filters ([GHSA-r27x][hasura-cve]).
- Directus CVE-2026-35442: `min`/`max` combined with `groupBy` skipped the concealed-field mask
  ([GHSA-38hg][directus-cve]).
- Directus CVE-2025-30352: `search` filtered on fields the caller couldn't view ([NVD][directus-cve2]).
- Directus CVE-2023-38503: subscriptions ignored permissions ([CVE-2023-38503][directus-cve3]).

**What we adopt:**
- The schema is built per caller from readable tables and visible columns. An unreadable table or hidden column is
  absent, and an unknown name gives the same message as a hidden one, with no suggestions beyond the caller's own
  schema.
- Every path an agent can take reaches the database through `ITableQueryService`: reads, filters, ordering,
  aggregates, group by, having, nested child reads and joins. That service already re-checks access per table and
  runs under row-level security (rls-raw-sql-agents-2026-11-10.md). The leak tests cover each of these paths
  separately, because that is where Hasura and Directus broke.
- Hard limits:
  - One query operation per call, with no mutations, subscriptions, fragments, variables or directives.
  - At most 4 table levels deep, 10 root fields and 15 aliases.
  - Query text capped at 10,000 characters.
  - A `limit` of 1 to 1,024 rows on each list, which is the structured tools' existing cap.
  - Nested reads capped at the same 1,024 rows per level.
  - The runner's 64 KB answer cap applied to the whole response.
  - The runner's existing statement timeout and work_mem.
- The caller's schema is returned by a `_schema` root field and with every validation error, which is Grafbase's
  pattern (sub-question 4). Real `__schema` introspection is refused.

### 4. LLM agents querying through GraphQL
No benchmark compares text-to-GraphQL with text-to-SQL on the same data. The GraphQL Foundation's AI working group
lists such a benchmark as future work ([GraphQL AI WG][gqlwg]). The only text-to-GraphQL accuracy study (IBM/StepZen,
EMNLP 2024) found that models of 3B–34B parameters scored under 15% zero-shot and about 50% with examples. Two-hop
nesting scored about 20%, and queries spanning several types scored 0%. The common errors were fields or endpoints that
don't exist, extra filters nobody asked for, and the right fields taken from the wrong endpoint ([IBM][ibm]). No
frontier model was tested, so these numbers set a floor, not a forecast for Sonnet.

The closest comparison of a constrained interface with SQL is dbt's 2026 rerun: 11 questions, 20 runs each, run by
the vendor. On questions its semantic layer covered, the semantic layer scored 100% against 62.5% for SQL with
Sonnet 4.6. On questions it didn't cover, it scored 0% against 70–100% for SQL ([dbt][dbt]). Its misses were errors,
while the SQL misses were plausible wrong numbers. Hasura moved its AI product off GraphQL to model-written Python plus
SQL plans ([Hasura PromptQL][promptql]). Microsoft's SQL MCP Server deliberately offers fixed read and aggregate tools
instead of model-written SQL ([DAB MCP][dab-mcp]).

For giving agents the schema, Apollo's MCP server reports about 40% fewer tokens with a minified schema, and fewer
calls with search than with introspecting one type at a time. Those are the vendor's numbers from one example
([Apollo][apollo]). Grafbase returns the relevant part of the schema whenever a query names an unknown field
([Grafbase MCP][grafbase-mcp]). Shopify's dev MCP adds a validate tool to catch made-up fields ([Shopify MCP][shopify-mcp]).

**What this predicts for CON-336:**
- On tables-v1, GraphQL covers what the structured tools cover. Its edge, if any, comes from asking for several
  tables or levels in one call.
- On the flexibility set, medians, ranks within groups, monthly totals and cross-column math are not in any
  generated GraphQL schema, ours included. The GraphQL agent will have to read rows and compute the answer itself, as
  the structured agent does. SQL should lead on those question kinds unless GraphQL's misses come back as visible
  errors. The report should count answers given wrong separately from answers not given.

## Design that follows
- **Tool:** `table_graphql(container_id, query)` returns `{"data": {...}}` with nested rows.
  - **Root fields:** each readable table gets `<name>(where, order_by, limit, offset, seen_as_of)` and
    `<name>_aggregate(where, group_by, having, order_by, limit, join)`. `_schema` returns the caller's schema as SDL,
    with each GraphQL name annotated with the table or header it stands for.
  - **Nested fields:** a child table appears as a nested field on its parent, joined on `_row` = `_parent_row`. Any
    other readable table can be nested with an explicit `on: {column: other_column}`. Each nested level is one
    batched read, matching the column `IN` the parent rows' values, so three-table joins are two levels of nesting.
  - **Names:** headers become valid GraphQL names. Characters outside `[A-Za-z0-9_]` become `_`, a leading digit gets
    `_`, and clashes get `_2`, `_3`. The schema keeps the original header beside each name.
  - **Gaps:** median, rank, month bucketing and cross-column math are left out, matching what every generated schema
    offers. Adding them would test features rather than the interface. If GraphQL proves the better interface, they
    can be added to the shared compiler for both the structured tools and GraphQL.
- **Parser:** GraphQL-Parser 9.5.1 (MIT, no dependencies), added to THIRD_PARTY_NOTICES.

## Conflicts and uncertainties
- **Whether Hasura DDN's GraphQL API exposes group by.** The connector spec defines grouping with date extraction,
  but no user docs show it, and an open issue says the Postgres connector lacks it. We treat it as unconfirmed.
- **Whether Hot Chocolate's dynamic types were renamed.** `*Definition` may have become `*Configuration` in v15/16,
  but the docs still show `Definition`. This doesn't matter, since we don't use Hot Chocolate.
- **Agent accuracy figures.** IBM's numbers come from small models. dbt's and Apollo's numbers are vendor-run on small
  sets. None is a forecast for Sonnet.
- **The "same 180 questions" rule.** The ticket requires CON-328's 180 questions, but `eval/pass-bars.md` says a
  result-informed change is re-tested on a sealed reserve set. The `table_sql` listing fix was informed by CON-328's
  results on those questions, so the SQL arm's tables-v1 score is not a clean re-test. The pass bar says so, and the
  flexibility set, written fresh for this ticket, is the clean comparison.

## Gaps — what we did not find
- Any study that compares agents writing GraphQL with agents writing SQL on the same data.
- Accuracy figures for text-to-GraphQL with frontier models.
- Published advisories for pg_graphql or PostGraphile. Snyk lists none for PostGraphile.
- Numeric guidance for field-duplication or directive-overloading limits; the token and alias caps cover them
  indirectly.
- Whether Hasura's per-role row fetch limit applies to nested queries.

## Source quality assessment
- **Sub-questions 1–3:** mostly primary sources, meaning vendor docs, specs, NuGet pages and published security
  advisories.
- **Sub-question 4:** one peer-reviewed study (IBM, EMNLP 2024, small models), vendor blogs (dbt, Apollo, Grafbase,
  Hasura) and a GraphQL Foundation meeting recap. The vendor numbers are single-source and come from small or
  self-run sets, so they are low confidence.
- **Prior Connapse notes:** the ones cited here were themselves built on primary docs.
