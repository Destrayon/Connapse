# Connapse v0.4.2

**Approve an agent's delete and Connapse carries it out. The agent no longer has to repeat it.**

If your agent waits with `approval_status` and then repeats a held delete, change it to read the batch with `deletion_status` instead and not repeat the call.

## What's changed

- **Every held delete is a batch Connapse carries out.** When an agent's token asks before deleting, a single delete now works like `request_deletions`: deleting a file, a folder, an empty container, a memory space or a memory fact, or up to 50 files at once, puts a batch on the Approvals page. Once you approve it, Connapse deletes the approved items itself, skipping anything that changed since the agent asked, and the agent reads each outcome with `deletion_status`. In v0.4.1 the agent had to wait for your approval and then repeat the call.
- `request_deletions` also takes empty containers and memory facts.
- Held calls that aren't deletions of your knowledge, such as setting a credential or removing a user, still work as before: the agent waits with `approval_status` and repeats the call once you approve it.
- **One tool each for reading, uploading and deleting files, one file or many.** `get_document` now reads up to 50 documents at once, `upload_file` uploads up to 100 files, and `delete_file` deletes up to 100, or up to 50 when the delete is held for approval, since a batch holds at most 50 items. They replace `get_documents`, `bulk_upload` and `bulk_delete`, which still work and give the same results but no longer appear in the tool list an agent loads. Those three old names will be removed after the 0.4.x releases, so switch any scripts or agent prompts that use them.
- A memory save now also lists the current facts with the same subject and attribute, so an agent sees what's already there; nothing is refused.

## Fixed

- Approving a held delete now skips a file that was replaced after the request, even with the same size and type.
- The warning "Could not check memory sources" no longer appears in the log after startup when a memory space page opens (#1201, reported by @marcusyoung). The counts you saw were never wrong.

## For MCP clients that hardcode tool names

`upload_file`, `get_document` and `delete_file` keep their names. Only the multi-file tools changed:

| Old name | Use now |
|---|---|
| `get_documents` | `get_document` with `files` (up to 50) |
| `bulk_upload` | `upload_file` with `files` (up to 100) |
| `bulk_delete` | `delete_file` with `fileIds` (up to 100, or 50 when the delete is held for approval) |

The old names still work in v0.4.2 and return the same results, but they are no longer in `tools/list`, so a client that checks the list before calling won't find them. They will be removed after the 0.4.x releases.

## Upgrade

If you started Connapse with the README's one-command start (`docker compose -f oci://ghcr.io/destrayon/connapse:compose up -d -y`), follow [Upgrade Connapse](https://github.com/Destrayon/Connapse/blob/v0.4.2/docs/self-host/upgrade.md) instead of the steps below. If you run a downloaded `docker-compose.yml`, first make a backup with [Back up and restore Connapse](https://github.com/Destrayon/Connapse/blob/v0.4.2/docs/self-host/backup-and-restore.md), since this release runs a migration and rolling back means restoring it. Then:

```bash
# in .env
CONNAPSE_VERSION=v0.4.2
```

```bash
docker compose pull web
docker compose up -d
```

From v0.4.1 there is no change to `docker-compose.yml`. One migration adds a column to the documents table; it runs when the app starts. From an older version, follow [Upgrade Connapse](https://github.com/Destrayon/Connapse/blob/v0.4.2/docs/self-host/upgrade.md), which covers each release in between.

Every change is in the [changelog](https://github.com/Destrayon/Connapse/blob/v0.4.2/CHANGELOG.md).
